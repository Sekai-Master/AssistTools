# ポイント調整アナライザー Step1〜3 再編ブリーフ

作成: 2026-07-24 / 前段: `point-adjust-step2-ux-brief.md`（コミット afb8b3a・f91b669 で実装済み）

## この改修の骨格

目標ポイントへの着地を、**Step3から逆算する**構造に整理する。

```
目標との差分
  − Step3（ラストプレイ）の獲得分
  − Step1（マイセカイ）の獲得分
  = Step2（ライブ調整）が埋める残額
```

現在は Step1 → Step2 → Step3 の順で組み立てているが、
**Step3 が「最後に何をするか」の宣言である以上、そこを先に決めて逆算する**のが自然。

## 0. 貫く原則: 常に最低限の入力欄しか見せない

**この改修全体を通じて徹底する。**いま意味を持たない入力欄は画面に出さない。

- ワールドパスのトグルは、マイセカイが ON のときだけ現れる
- ラストプレイの「希望ポイント」は、そのモードを選んだときだけ現れる
- ラストプレイの曲選択は、「指定しない」を選んでいる間は現れない
- Step2 の「イベントボーナス選択」はモードA（曲固定）のときだけ、
  「曲選択」はモードB（編成固定）のときだけ現れる
- スコア上限などの詳細設定は既定で畳む

利用者は**スマホ片手でゲームと行き来しながら**使う（`projects/point-analyzer.md`）。
選ばなくてよい入力が見えていること自体が判断コストになる。
**「後で使うかもしれないから出しておく」を禁止する。**

判断に迷ったら「この欄は今この瞬間、意味があるか？」で決める。
意味が無いなら出さない。モードを切り替えた瞬間に現れればよい。

## 1. Step3 = ラストプレイの3択

排他選択。選んだモードに応じて入力欄を出し分ける。

| モード | 曲選択 | 希望ポイント入力 |
|---|---|---|
| **ラストプレイを指定しない** | 非表示 | 非表示 |
| **ラストプレイで希望するポイントを稼ぐ** | あり | **あり（必須）** |
| **ラストプレイをスコア0でクリアする** | あり | 非表示（自動算出・表示のみ） |

- **曲が未選択のときは自動で割り当てる。**ロジック的に決め打ちが素直なら
  独りんぼエンヴィー（基礎点100・74.8秒）を既定にしてよい
- 「スコア0でクリア」は前ラウンドで Step2 に入れた `lib/scoreZeroFinish.ts` を移設して実現する。
  締め値は `calcLivePt(基礎点, bonus, 0, LB)` から動的導出（ハードコード禁止）
- 「希望するポイントを稼ぐ」は既存のラストラン（`lib/finalRun.ts` のボーナス掃引）がそのまま対応
- **既定は「指定しない」**
- モード切替時、隠れた入力値が計算に残り込まないこと

### Step2 側の後始末

Step2 の「スコア0イベ乙」「同じ曲だけで組む」トグルは**両方削除**する
（前者は Step3 へ移設、後者は要求から外れた）。
`lib/sameBaseAdjust.ts` の処遇（削除 or エビ調整への転用）は設計者が判断し理由を残すこと。

## 2. マイセカイ（Step1）の既定を OFF にする

- **現在の既定は ON だが、この設計は中途半端なので既定を OFF に振る**
- **ワールドパスのトグルは、マイセカイが ON になったときに初めて現れる**ようにする
  （現在は常時表示。マイセカイOFF時には意味を持たない入力）
- マイセカイを使う設定のときは、基本的に Step3 側で詰める

### Step1 の配分が Step2 を詰ませる問題（実バグ）

`constants.ts` の `LIVE_ADJUST_RESERVE = 100`（マイセカイ配分後にライブ端数調整用として残すPt）
は、**1本の最小獲得Ptを下回っている**。ボーナス990%・基礎点100・LB0・スコア0 で最小は **1,090**。
残額が 1,090 未満だと Step2 は原理的に着地できない。さらに前ラウンドの実測では、
**1,090〜6,807 の帯には3本以内で作れない値が200個以上**ある（安全域は 6,808 以上・ボーナス990%時）。

**Step1 で取りすぎて Step2 が着地不能になることを防ぐ。**
ただし必要な確保額は **Step2 がどちらのモードか**で2桁変わる。実測（2026-07-24）:

**ボーナスを 0.5%刻み（`BONUS_STEP_10X`）で振ると、1本（LB0・スコア0）の到達値は隙間ゼロで連続する。**

| 曲の基礎点 | 到達範囲（ボーナス0〜990%） | 通り数 | 隙間 |
|---|---|---|---|
| 100（エビ） | 100 〜 1,090 | 991 | **0箇所** |
| 107 | 107 〜 1,166 | 1,060 | **0箇所** |
| 130 | 130 〜 1,417 | 1,288 | **0箇所** |

ボーナス0%のとき1本の獲得は**ちょうど基礎点そのもの**になる（エビ=100）。これが下限で、
エビの場合 1〜99 だけが作れず、**100以上はすべて作れる**（3本以内・全数チェック済み）。

したがって:

| Step2 のモード | 確保すべき額 |
|---|---|
| **A. 曲固定＋ボーナス可変** | **選んだ曲の基礎点**（エビなら100・メルトなら130） |
| **B. ボーナス固定＋曲可変** | そのボーナスでの安全域（990%なら 6,808） |

**`LIVE_ADJUST_RESERVE = 100` は「エビの基礎点」であり、モードAでは正確に正しい。**
バグではなく、モードBの存在を想定していないだけ。よって定数を単純に大きくするのではなく、
**Step2 のモードと選択曲から確保額を導出する**こと。

補足: モードAは刻みを細かくするほどボーナス編成を外す手間が増える（0%＝ボーナス編成を全部外す）。
組み替えコストとして提示に含めると親切。

## 3. Step2 = 調整の2モード

**「曲を固定してボーナスを動かす」か「ボーナスを固定して曲を動かす」かの選択**にする。

| モード | 曲 | イベントボーナス | 提示内容 |
|---|---|---|---|
| **A. 任意の曲を使って調整する**（既定の曲はエビ） | 固定（選択可・既定エビ） | **選択させる**（編成を組み替える前提） | 目標ボーナス値 |
| **B. 入力された編成を使って調整する** | **該当基礎点の曲から選択** | 固定（入力値） | **複数プラン。総プレイ時間が短い順を優先** |

- **A はこのツールの主用途**。`projects/point-analyzer.md` が
  「独りんぼエンヴィーをソロ・ライブボーナス0〜1消費で叩く端数調整」と定義しているもの。
  現在この経路は `lib/liveAdjust.ts` のボーナス掃引として存在するが、
  R2 の改修で `calculator.ts` L168 付近で**「第2候補」に降格されている**。これを是正する。
  エビだけで細かく刻むには現行ボーナスでは粒度が粗い（990%だと最小1,090Pt刻み）ため、
  **ボーナスを下げる＝編成を組み替える**必要がある。掃引が返す目標ボーナス値を、
  ユーザーが実際に編成を組める形で提示すること
- **B は前ラウンドで実装した複数回プラン（`multiLiveAdjust.ts`）**がそのまま対応する。
  総プレイ時間の短さを優先する（`planDuration.ts` が既にある）
- 探索ロジックは作り直さない。位置づけと提示を変える

## 4. ジャケット画像

- `plan/PlanCard.tsx` は既に `jacketSrc` を描画し、`lib/adjustPlanCanvas.ts` も
  `jacketUrl` を扱う。**新設した `steps/liveAdjust/` 配下にだけ無い**
- ジャケットは `public/MusicDatas/jacket/`、参照パスは `PointAnalyzer.tsx` の `JACKET_BASE`
- 読み込み失敗時は既存の `onJacketError`（`src/lib/img`）に合わせる
- **スマホ片手前提。ジャケットで縦の情報密度を落とさないこと**（小さめのサムネイル）

## 5. 「全力」タグを削除

スコア帯バッジの「全力」は意味が伝わらないため**削除**する。
「放置」（叩かなくてよい＝実行が確定する）は実用的な情報なので残す。
`FULL_POWER_BAND_MARGIN` が不要になるなら合わせて整理すること。

## 6. ライブボーナス回復時間の表示を削除

プラン見出しの「（回復 約4.5時間・クリスタル約90個）」のうち、**回復時間は表示しない**。
待てば回復する資源であり、判断材料にならず画面幅を圧迫するだけだった。
クリスタル換算を残すかは実装者の判断でよい。

## 7. Step1〜3の統合画像出力

- **Step3 の下**に配置。「コピー」（クリップボード）と「保存」（ダウンロード）の2つ
- 現在 `lib/adjustPlanCanvas.ts` が Step2＋ラストランを描いている。**Step1 を含む全ステップ版**へ拡張
- **実施しないステップはスキップして詰める**（マイセカイOFFなら Step1 なし、
  Step3 が「指定しない」なら Step3 なし）
- 既存のコピー実装（`LiveAdjustStep.tsx` の `canvas.toBlob` → `ClipboardItem`）を踏襲
- **スコア0クリアの「叩かない」が画像に出ること**
- ジャケットを画像にも載せる

## 勝利条件

1. Step3 の3択・Step2 の2モードが排他で、選択に応じた入力欄が過不足なく出る
2. 主用途（エビ＋編成組み替え）が「第2候補」ではなく正当な位置に提示される
3. **Step1 が取りすぎて Step2 が着地不能になる経路が塞がれている**
4. Step1〜3 が1枚の画像に出せて、実施しないステップは詰められる
5. ジャケットが出て、スマホ片手での縦密度が悪化していない
6. **既存の計算結果（厳密一致・回数最小性）を1ptも壊さない**

## 禁じ手

- **ON経路（マイセカイ利用時）の計算結果を変えないこと。**
  `calculator.test.ts` / `liveAdjust.test.ts` の凍結テスト・ゴールデンは1文字も触らない
  （既定値の変更はUIの初期状態の話であり、計算結果の変更ではない。混同しないこと）
- `planMultiLiveAdjustment` の frontier構築ループ・best選択セマンティクスを改変しない
- ボーナス掃引（`liveAdjust.ts` / `finalRun.ts`）の探索ロジックを作り直さない
- マジックナンバー禁止。締め値・確保額・閾値は定数か `calcLivePt` から導出
- 800行超のファイルを作らない
- 前ラウンドのテスト網（`steps/liveAdjust/*.test.ts`）を機能削除に伴ってまとめて消さない。
  残る機能の分は移植すること

## 受け入れ条件

- `npx tsc --noEmit` exit 0 / `npx vitest run` 全通過 / `npm run build` 成功
- ON経路の凍結テスト・ゴールデンが無変更で通過
- Step3 の3モード × Step2 の2モード × マイセカイ ON/OFF の組合せについて、
  入力欄の出し分けと計算への反映を固定するテスト
- **Step1 の確保額がボーナス依存で動的に決まり、Step2 が着地不能にならないことのテスト**
- 統合画像出力について、スキップ時に詰められることを検証するテスト
- 曲未選択時に自動割当が働くことのテスト
