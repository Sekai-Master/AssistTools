## 3. 古い URL の扱い

**過去ポストは消さない。** 削除しても他人の引用・RT・ブックマーク・検索結果には痕跡が残り、**行き先だけが消える**ので誰も救われない。加えて、規約に窓口として載せたアカウントの過去が空だと、実体不明の新設アカウントに見える。直し方は「新しい固定ポストで上書き」と「必要な分だけ訂正リプ」。

URL は4世代あり、**生死が違うので対応も違う**（2026-08-04 に全世代を実測）。

| 世代 | URL | 状態 | 対応 |
|---|---|---|---|
| ① Google Drive 公開 | `projectsekai-ruler-tweet.on.drv.tw/Sekai-Ruler/…` | **応答なし**（接続タイムアウト） | 踏むと待たされるうえサイト名も違う。代表的な投稿に訂正リプ |
| ② GitHub Pages | `sekai-master.github.io/AssistTools/` | **404** | 同上 |
| ③ Netlify | `sekaimaster.netlify.app` | **301 で生存**（クエリも引き継ぐ） | **何もしなくてよい** |
| ④ Cloudflare Pages | `sekaimaster.pages.dev` | 現行 | — |

**一番効くのはプロフィールのリンク欄**（対応済み）。古い投稿を見た人は結局プロフィールに飛ぶ。訂正リプは代表的な1〜2件で足りる。

### イベントの開始日時は過去データから読める

次イベがマスタDBに載るのは公開直前なので、告知を組む時点では未確定なことが多い。ただし**過去の実績から高い確度で読める**（2026-08-04 に直近14件を集計）。

- **前イベの集計終了から次イベ開始までの間隔は 42〜43h か 47h の2択**。他の値は出ていない
- **開始時刻は種別で決まる**。`marathon`（通常）は 10件すべて **15:00**、`world_bloom`（ワールドリンク）は 4件すべて **20:00**。例外なし。**20時開始はワールドリンクだけ**（2026-08-04 Nori 確認）
- したがって **日付は集計終了の翌々日でほぼ確定**し、時刻は種別さえ分かれば決まる

集計方法:

```bash
curl -s https://raw.githubusercontent.com/Sekai-World/sekai-master-db-diff/main/events.json -o events.json
# startAt / aggregateAt / eventType を見て、間隔と開始時刻の分布を出す
```

### 編成の話は「イベント開始」ではなく「ガチャ開始」に当てる

**ガチャは種別に関係なく必ず 12:00 に始まる**（直近8イベントで例外なし。2026-08-04 に `gachas.json` で確認）。

| イベント種別 | イベント開始 | ガチャ開始 | 差 |
|---|---|---|---|
| marathon（通常） | 15:00 | **12:00** | 3時間 |
| world_bloom（WL） | 20:00 | **12:00** | 8時間 |

つまり「イベント開始の3時間前」ではなく「**12時に必ず開く**」。そして**ガチャが開いた時点でボーナス対象のタイプとメンバーが分かる**ので、編成をどう組むかの検討はそこから始まる（2026-08-04 Nori 指摘）。

- **編成ビルダーの告知は 12:00〜12:30 に置く。** イベント開始（15:00）を待つと、多くの人は組み終わっている
- ゲージ・周回プラン・稼働時間のような「走り方」の話は、イベント開始後でよい
- 種別が未公開でも**日付とガチャ開始時刻は読める**ので、編成系の告知だけは先に予約を入れられる

- **ツールごとに「要る時期」が違う。** 編成ビルダーはイベント開始時、アナライザーは終盤。機能紹介はイベントサイクルのどこに刺さるかで並べる
- 21時は業界一般の定石であって、このアカウントの実測ではない。**Cloudflare Web Analytics を 2026-08-04 に入れた**ので、データが溜まったら実際のアクセス時間帯で組み直す
- X の予約投稿は **Web 版の投稿画面（カレンダーアイコン）から**。スマホアプリからはできない

## 7. 平常時の告知テンプレ

### リリース告知（MINOR 以上のとき。PATCH は出さなくてよい）

**利用者から見た違いを先に書く。** 版番号や内部の話から始めない。

```
【更新 v1.10.0】
（使う人から見て何ができるようになったかを1〜2行）

くわしくは → https://sekaimaster.pages.dev/changelog
```

### 新ツールを出したとき

```
【新ツール】○○を追加しました。
（何ができるかを1行。使う人の困りごとから書く）

https://sekaimaster.pages.dev/○○
#プロセカ募集 #プロセカ協力
```

### 不具合を見つけた／報告をもらったとき

```
【不具合】○○で△△になる問題を確認しています。原因を調べています。
直り次第このポストにぶら下げて報告します。
```

```
【復旧】先ほどの○○は直しました。報告してくださった方ありがとうございました。
```

**不具合は隠さずに出す。** 計算ツールは「合っている前提」で使われるので、間違っていた期間があったこと自体が利用者にとっての情報になる。

### 規約・ポリシーを改訂したとき（情報の扱いが変わる場合は必須）

```
【お知らせ】プライバシーポリシーを改訂しました（施行 2026-○-○）。
変更点: ○○
https://sekaimaster.pages.dev/privacy
```

## 8. 運用の約束

- **約束するのは「見ていること」だけ。** 返信期限は名乗らない（個人の趣味なので守れない）。規約にも書いていない
- 不具合の報告は、記録が残る **GitHub Issues** に誘導してよい。ただし「Issues じゃないと受け付けない」とは言わない。アカウントを持っていない人が大半
- **権利者（セガ・Colorful Palette 等）からの申し入れは最優先**。来たら実装より先に対応する（規約第3条）
- なりすましや、本サイトを公式と誤認させる投稿を見つけたら、固定ポストで「非公式」を再掲する
- 宣伝以外の雑談はこのアカウントでやらない（運営者個人のアカウント **@YesNoritake** と役割を分ける）。ここが雑談で埋まると、告知が流れて見つからなくなる
- 逆に **@YesNoritake は窓口にしない**。利用規約にもそう書いてある（第1条で運営者の同定のために載せ、第7条で「窓口ではない」と明記）。個人宛に不具合報告が来たら、公式アカウントか Issues へ誘導する

## 9. リリース手順との接続

告知は[リリース手順](versioning.md#リリース手順)の**最後の工程**。順番は変えない。

1. デプロイが本番に反映されたことを確認する
2. `/changelog` に新しい版が出ていることを確認する
3. **そのうえで**告知する

先に告知すると、見に行った人が古い版を見る。
