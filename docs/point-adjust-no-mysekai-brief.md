## 2. 現状の設計（正確に把握してから触ること）

### データフロー

`PointAnalyzer.tsx`（UI・入力）→ `calculatePlanV6()`（`lib/calculator.ts`、オーケストレーション）→ 各モジュール。

```
calculatePlanV6(currentPt, targetPt, finalRunPt, talent, bonus, hasWorldPass, finalSongId, musicsList)
  1. unitBasePt   = calculateUnitBasePt(talent, bonus, hasWorldPass)   // mySekai.ts
  2. totalDiff      = targetPt - currentPt
     adjustableDiff = totalDiff - finalRunPt
  3. allocation   = allocateMySekai(adjustableDiff, unitBasePt)        // mySekai.ts ★ここが対象
  4. liveRequired = adjustableDiff - allocation.totalPt
     live         = planLiveAdjustment(liveRequired, bonus)            // liveAdjust.ts
  6. finalRunPlans= planFinalRun(finalRunPt, finalBase, bonus)         // finalRun.ts
  7. estimatedTotal = currentPt + allocation.totalPt + liveAdjPt + finalRunPt
     isVerified     = estimatedTotal === targetPt && live.status === "OK"
```

### 各モジュールの責務

| ファイル | 役割 |
|---|---|
| `lib/calculator.ts` | 上記の順に呼びログと検証をまとめるだけ。計算の実体は持たない |
| `lib/mySekai.ts` | マイセカイ単価と採取配分。`allocateMySekai` が差分の**大部分を吸収**する |
| `lib/liveAdjust.ts` | ライブ1回（LB 0〜1・エビ基礎点100固定）で端数を**ちょうど**埋めるスコア帯を逆算 |
| `lib/finalRun.ts` | ラストランのプラン列挙 |
| `lib/constants.ts` | 定数。`LIVE_ADJUST_RESERVE = 100`、メモリ値 A=1.0/B=0.5/C=0.2 |
| `steps/MySekaiStep.tsx` / `LiveAdjustStep.tsx` / `FinalRunStep.tsx` | 結果表示 |

### 役割分担の要点（ここが設計の心臓）

- **マイセカイ＝粗い大量吸収役**。単価 `unitBasePt` は1メモリあたり（実測例: 総合力297,159・ボーナス615% → 1100 Pt/メモリ）。
  最小粒度は C = 0.2メモリ ≒ `0.2 × unitBasePt`（上例で約220 Pt）。これで**百万単位の差分を粒度220Ptまで削る**。
- **ライブ端数調整＝最後の微調整役**。`allocateMySekai` は `LIVE_ADJUST_RESERVE`(=100Pt) を必ず残す。
  `planLiveAdjustment` は**ライブ1回ぶん**しか解かない（`ADJUST_LIVE_BONUSES = [0, 1]`、基礎点100固定、スコア係数 N は 0〜200）。
  → **1回のライブで到達できるポイントは高々数千Pt程度**。百万単位は絶対に解けない。

## 3. ★中核の設計論点（単純にスキップすると壊れる）

`allocateMySekai` を単に飛ばすと `liveRequired = adjustableDiff`（＝百万単位になりうる）が
そのまま `planLiveAdjustment` に渡る。上記のとおりライブ1回では解けないので **`status: "NG"` が返り、
UI は「この条件では目標ちょうどに着地できません」を出す。つまり素朴な実装は "常にNG" の使えない機能になる。**

**マイセカイを外すと「差分の吸収役」が消える** ——これが本質。ここをどう設計するかが本タスクの主論点。

### 候補案（監督が選ぶ / 別案でもよい）

**A案: 素直にスキップ＋不能時の明示ガイド**
マイセカイ配分を0にし、ライブ端数調整＋ラストランで埋まる範囲だけ「着地可能」とする。
埋まらない場合は NG ではなく「マイセカイ無しでは到達不可。マイセカイ無しで狙える差分は最大◯Pt」と
**理由と代替を明示**する。実装が軽く、嘘をつかない。ただし大差分では機能しない。

**B案: 調整ライブを複数回許す**
`planLiveAdjustment` を「N回のライブで合計 liveRequired ちょうど」に拡張（回数上限を設ける）。
吸収力は上がるが探索が重くなりがちで、ちょうど着地の組合せ爆発に注意。

**C案: 通常周回ライブを吸収役に据える**
「普通に周回するライブ K 回」で粗く詰め、最後の1回で端数調整。
※ただし通常ライブの獲得ptはスコア次第で揺れるので「ちょうど着地」の保証が弱い。
マイセカイが吸収役に選ばれている理由がまさにこれ（採取は取得数が決定的で揺れない）である点に注意。

**推奨の出発点**: A案を土台に、必要なら B案を足す。C案は「ちょうど着地」というツールの根幹保証を壊しやすいので慎重に。
ただし最終判断は監督に委ねる。**「常にNGになる素朴スキップ」だけは避けること。**

## R2-4. 推奨アプローチ（素朴な全探索は爆発するので注意）

複数回を許すと「合計をちょうど liveRequired にする組合せ」は subset-sum になり、
`liveRequired` が大きいと素朴なDP・全探索は破綻する（目標が百万級だとDP配列が持てない）。

推奨する分解:

1. 固定ボーナス下で**1回のライブが取りうる到達Pt集合 S** を列挙（28基礎点 × LB0〜10 × スコア係数）。
   各到達Ptに対し「最も安い実現手段（LB少・回数少）」を代表として持つ。
2. `maxPt = max(S)` から**必要最小回数 n = ceil(liveRequired / maxPt)** を出す。
3. **n−1回を「大きい値」で埋め、残りを既存の単発厳密探索で解く**。
   つまり全組合せを回すのではなく、*端数だけ*を既存の正確な逆算に委ねる。
   端数が S に無くて解けない場合は、bulk 側のスコア係数を ±1 ずらして再試行する
   （スコア係数刻みで到達Ptは細かく動くので、数回の摂動で収束する）。
4. これで計算量は「既存の単発探索 × 定数回」に収まり、**厳密着地の保証も維持される**。

このアプローチに従う義務はない。より良い方法があれば採ってよい。
ただし **UIが固まらないこと**は必須（`constants.ts` の `MAX_SEARCH_BONUS_10X` のコメントに、
探索70万回でUIが数秒固まった過去の事故が記録されている。同じ轍を踏まないこと）。

## R3-0. 最優先: スコア上限400万点という非現実的な前提【CRITICAL】

### 何が起きているか

`MAX_SCORE_N = 200` × `SCORE_STEP = 20000` = **スコア4,000,000点**を「到達可能」の上限として使っている。
複数回探索は回数最小化のため1回あたり獲得Ptを最大化するので、**必然的にこの上限に張り付く**。

実測（ボーナス435%・現在50万→目標100万・ラストラン3万）:
```
liveRequired=470,000, isVerified=true, 第1候補:
  全7回 LB合計64
    基礎点130 ・ 10炊き ・ スコア 4,000,000〜4,019,999 × 6回
    基礎点107 ・  4炊き ・ スコア 3,580,000〜3,599,999 × 1回
```
→ **400万点のソロライブを6回**という、人間に実行不能な指示。
liveRequired を5万〜200万で総当たりすると、593ライブ中 **583回が300万点超**を要求していた。

### これは移植時に既知のリスクとして文書化されていた

`docs/porting/03-analyzer.md:26`:
> React版はMAX_SCORE_N=200固定・SCORE_STEP=20000で最大4,000,000までカバーする一方、
> vanilla版はmaxScore（UIの詳細設定、**既定1,100,000**、内部で3,000,000にクリップ）までしかループしない。
> **この探索上限の違いは大きなスコア帯を要する高倍率ボーナス時に結果の差になりうる**

同 `:70`: 「maxScoreの概念はReact版では固定探索上限に置き換わっており、**ユーザーが変更できるUI要素としては存在しない**」

ON経路では `liveRequired` が数百Ptなので低スコア帯で解けて表面化しなかった。
R2の複数回モードがこの潜在バグを起爆した。

### 波及（ここが本丸）

`maxPtPerLive` が約1.94倍に膨らむ（73,010 vs スコア上限110万時 37,695）。
したがって `minCount = ceil(liveRequired / maxPtPerLive)` は**全部過小申告**:

| liveRequired | 現在の提示 | スコア上限110万での理論最小 |
|---|---|---|
| 100,000 | 2回 | 3回 |
| 500,000 | 8回 | 14回 |
| 1,000,000 | 15回 | 27回 |

`OVER_CAP` の閾値も同じ理由で壊れている（差分4,980,000で「最低69回」と出すが、110万上限なら133回）。
**「50回以内で着地できます」と `isVerified: true` を返しているケースが、現実には50回を超える。**

### 依頼者の決定（確定事項・再検討不要）

**スコア上限をユーザー設定可能にする。既定 1,100,000。** 移植元vanilla版と同じ設計。
- 「環境設定」パネルに入力欄を出す（詳細設定として畳んでよい）。
- 内部で 3,000,000 に上限クリップ（vanilla版と同じ安全弁）。
- **ON経路にも適用する。** 400万点が不可能なのはモードに関係ないため。
  これにより第2候補（`collectScorePlans` のボーナス掃引）の提示が変わりうる。
  **変わった場合はON凍結テストの改訂を許可する**（依頼者承認済み）。
  ただし改訂する場合は「なぜ変わったか」をテスト内コメントとコミットメッセージの両方に明記すること。
  無変更で済むなら、それが望ましい。

## R3-1. ライブボーナスを実質無料資源として扱っている【CRITICAL】

実測した第1候補の `lbCost`（ボーナス435%）:

| liveRequired | 回数 | LB合計 | 自然回復のみ(30分/個) | クリスタル換算 |
|---|---|---|---|---|
| 100,000 | 2 | 10 | 5時間 | 100個 |
| 500,000 | 8 | 63 | 31.5時間 | 630個 |
| 1,000,000 | 15 | 140 | 70時間 | 1,400個 |
| 3,500,000 | 48 | 480 | **240時間(10日)** | 4,800個 |

UIは「全48回 ・ LB合計480」という生数字だけ。**所持上限10個という事実にも、480個貯めるのに10日かかることにも触れていない。**
さらに `planFinalRun`（`lib/finalRun.ts`）はラストラン側でもLB 0〜10を使うので実際の総消費は「調整480 + ラストラン最大10」だが、
**両ステップを合算した総LB表示がどこにもない**。

皮肉なことに `liveAdjust.ts:47-50` のコメント自身が「端数調整は安い操作であるべきなので0〜1に縛る」と正しい設計思想を書いている。
OFFモードでこの縛りを外したのに、外したコスト（狙い撃ちを1回外すとライボ10個が消える）を開示していない。

### 要件

- LB合計に**時間換算（30分/個）とクリスタル換算（10個/個）を併記**する。
- **ラストランのLB消費と合算した総消費**を出す。
- 所持上限10個を超える要求には、それが分かる注記を出す。

## R3-2. 「5案から選べる」が見かけ倒し【CRITICAL】

`minCount` で解が1つでも見つかった瞬間に return するため、**第2キー（LB昇順）が同一 n の中でしか効かない**。
結果、提示される5案に意思決定に効く多様性がない:

```
req=100,000: 2回/LB10 | 2回/LB10 | 2回/LB10 | 2回/LB10 | 2回/LB10
req=300,000: 5回/LB38 | 5回/LB38 | 5回/LB38 | 5回/LB39 | 5回/LB39
```

裏に隠れている選択肢（同じ2値構造での実測）:

| liveRequired | 現在の提示 | 隠れている案 |
|---|---|---|
| 20,000 | 1回 / LB4 | **10回 / LB0** |
| 100,000 | 2回 / LB10 | **48回 / LB0**（上限50回以内） |
| 300,000 | 5回 / LB38 | **6回 / LB30**（1回増やすだけでLB8個＝4時間ぶん節約） |

プロセカのライブは回数自体がほぼ無料（スタミナ消費なし）で、**ライボが律速資源**。
現状は優先順位が実際のコスト構造と逆になっている。

### 依頼者の決定（確定事項・再検討不要）

**「回数 vs LB」のトレードオフで並べる。** 回数最小案・LB最小案・その中間を並べ、ユーザーが選べるようにする。
- `minCount` で即 return するのをやめ、**上限まで（または実用的な範囲で）走査してトレードオフ曲線を作る**。
- 同じ回数・ほぼ同じLBの案でカードを埋めない（曲と帯が違うだけの案は代表1つでよい）。
- 各案に回数・LB合計・時間換算が並んで比較できること。
- **注意**: R3-0 でスコア上限が下がると1回あたり到達Ptが半減し、必要回数が増える。
  トレードオフ曲線も変わるので、R3-0 を先に直してから曲線を作ること。

## R3-3. NO_EXACT の死角と文言【HIGH】

ボーナス435%での1ライブ最小獲得Ptは `calcLivePt(100, 435, 0, 0) = 535`。
つまり **liveRequired が 1〜534 Pt のときは原理的に1回では不可能**（ボーナス800%なら1〜899 Pt）。

現在のUI文言は「目標を数ポイントずらすか」。**数ポイントでは絶対に抜けられない。**

構造的な原因: ON経路には `LIVE_ADJUST_RESERVE = 100` という「端数調整に必ず仕事を残す」保険があるが、
**OFF経路には `liveRequired` が死角に落ちないようにする仕組みが一切ない**（`liveRequired = adjustableDiff` そのまま）。

### 要件

- 死角に落ちた場合、**実際に必要なズラし幅**（最小到達Pt）を具体的な数値で案内する。
- 「数ポイント」のような不正確な表現をやめる。

## R3-4. その他の指摘（優先度順）

### MEDIUM: `maxLiveAdjustPt` の丸めによる誤NG（ON経路のリグレッション）
`lib/liveAdjust.ts` の `maxLiveAdjustPt` は `Math.floor(bonus * 10) / 10` で評価するが、
経路5.1は**丸めない `bonus`** で探索する。小数の細かいボーナスで上限が過小評価され、
R1で追加した早期returnが「旧コードなら解けた入力」を弾く。

再現: `planLiveAdjustment(4505, 200.34)` → HEAD: NG / origin/main: OK
（`findScoreStep(100, 200.34, 1, 4505) === 200`、guard=4500 に対し実際の到達は4505）
0〜1000%を0.01刻みで走査すると100,001値中9,000値で過小評価。
`parseAmount(bonus, true)` は `parseFloat` なので `200.34` は入力可能。
既存テスト `liveAdjust.test.ts` はこの不変条件を検証しているが整数ボーナスしかサンプルしていない。

### MEDIUM: 「n回すべてでスコア帯を狙い撃つ」負担の明示不足
「27回」の重さと、外したときにライボが無駄になるリスクが伝わっていない。

### LOW: 負の `liveRequired` で62,000回の `calcLivePt` を無駄に回す
`multiLiveAdjust.ts` の符号チェックが `reps` 構築ループの**後**にある。前に移すこと。

### LOW: `maxPtPerLive: 0` が自身の契約に矛盾
`liveRequired === 0` の経路で `maxPtPerLive: 0` を返すが、doc は「1回のライブで到達できる上限Pt」と書いている。
これで割る消費者が `Infinity` を得る。

### LOW: `maxAdjustablePt` が死んでいる
`calculator.ts` が公開しているが**どのコンポーネントも読んでいない**（grep 済み）。
かつ `ADJUST_BASE = 100` 固定で計算されており、OFFモードの第1候補は基礎点130まで使うので値として不正確。
R1の「NG時に限界値を示す」要件が実際には未実装。使うか消すか決めること。

### LOW: `distinctBasePoints` が非整数を通す
`Number.isFinite && > 0` しか見ていない。`basePoint: 113.5` を食うと「基礎点113.5」という
曲候補ゼロのプランができる。`Number.isInteger` が正しい述語。

### LOW: Step③で曲を変えるとトグルの現在値が黙って適用される
`PointAnalyzer.tsx` の `recalcWithSong` が state の `useMySekai` を読むため、
計算実行後にトグルを触ってから「曲を変更」を押すと、計算ボタンを押していないのにモードごと結果が入れ替わる。

### 参考: 誤検出ではなかったもの（対応不要）
- 探索窓 `EXTRA_COUNT_TRIES` の取りこぼし: 実測0件。ただし R3-0 でスコア上限が下がると到達Pt集合が激減するので**再評価が必要**。
- 3値以上でしか解けない `NO_EXACT` の反例: 現状の到達Pt集合が密（最小535・以後おおむね5Pt刻み）なため実測0件。これも R3-0 後に再評価。
- ラストラン不可侵: 違反なし。
- 厳密一致（2,400ケースのファズ）・ON経路の不変性（1,680ケース比較）: 違反なし。
