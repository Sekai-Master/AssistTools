# モードA（曲固定・ボーナス可変）を選択肢提示型にする ブリーフ

作成: 2026-07-25 / 前段: `point-adjust-step3-and-envy-brief.md`（コミット 8e18248・58e59da で実装済み）

## 問題（実機フィードバック）

モードA（任意の曲＋ボーナス可変）が、7,809 のような小さい端数に対して
**「目標ボーナス 397%」という非現実的な組み替え案を自動採択して1案だけ出す**。

- 現在ボーナス（例 990%）から 397% まで落とすのは、イベランの編成をほぼ捨てること。誰もやらない。
- しかも1案だけ＝ユーザーが選べない（「選択の余地なし」）。
- 根本原因: モードAの最適化軸が **「回数最小」** になっている。回数を1つ減らすために
  ボーナスを大きく下げる案を選ぶ。減らすべきは回数ではなく **「編成をいじる量」**。

## 方向（Nori 合意済み）

**earn モード（ラストプレイ＝希望ポイント）と同じ「複数候補を提示 → ユーザーが選ぶ」形にする。**

- **現在ボーナス維持（編成をいじらない）を最上位**に置く。1回で無理なら複数回でよい。
- 組み替え候補は **「下げ幅が小さい順」**（990%→900%→850%…）で下に並べる。
  397% のような極端な案は下に埋もれる（削除はしない＝選びたい人は選べる）。
- 各候補に「回数・スコア帯・LB・目標ボーナス」を表示。earn の候補カードと同じ粒度。
- 選んだ候補が **統合画像・合計に反映**される（earn の finalRunPlans 選択と同じ構造）。

### 重要な割り切り（UI に明記する）

ツールは編成データを持たないので **「どのボーナスが実際に組めるか」は判定できない**。
候補（ボーナス × 回数 × スコア帯）を並べて、**ユーザーが自分の編成で「組めそう」を選ぶ**。
earn も同じ（曲は選べるが「その曲を持っているか」は判定していない）。
「組める編成を選んでください」という趣旨の注記を添える。

## 現状の材料（作り直さず組み替える）

- `lib/liveAdjust.ts` 5.1 = `targetScoreRange`（**現在ボーナスのまま1回**で着地できるスコア帯）
- `lib/liveAdjust.ts` 5.2 = `adjustmentPlans`（**編成組み替え**で別ボーナスにする候補・複数・byBonusDesc）
- `lib/modeAMulti.ts` = 現在ボーナスを含めボーナスを振って**複数回**で着地（現状は「単発も組み替えもダメな時の代替」扱い）
- `steps/liveAdjust/BonusSweepPanel.tsx` = 画面で targetScoreRange と recommendPlans を出している
- `steps/FinalRunStep.tsx` / `plan/PlanSelectionUI.tsx` = **earn の複数候補選択UI**（これを参考にする）
- `sweepSelectedPlan` / `onSweepSelectPlan`（PointAnalyzer）= モードAの採択 state。統合画像が読む

## 要件

1. **候補リストを統一的に構築する**（純関数・テスト可能）。並び順は「編成変更が小さい順」:
   1. 現在ボーナス維持・1回（targetScoreRange があれば）
   2. 現在ボーナス維持・複数回（modeAMulti を**現在ボーナス固定**で解いた結果。
      ボーナスを振らず現ボーナスだけで複数回。ここが「編成いじらず回数で吸収」の主役）
   3. 組み替え・少ない回数（adjustmentPlans や modeAMulti のボーナス可変結果）を
      **現在ボーナスからの下げ幅が小さい順**に
   - 各候補は「目標ボーナス（現ボーナスなら『編成そのまま』）・回数・スコア帯・LB・獲得Pt」を持つ
2. **earn 風の選択UI**（候補カードのリスト・選択状態・スマホ片手で選べる）。
   既定選択は先頭（＝編成そのまま）。
3. **選択が統合画像・合計・footer に反映**される。
4. 「組める編成を選ぶ」注記。ツールは組める判定をしない旨。

### モードA複数回化（modeAMulti）の使い分けに注意

現状 modeAMulti はボーナスも振って「回数最小」を選ぶため 397% を出す。
今回は **(a) 現在ボーナス固定で複数回** と **(b) ボーナス可変** を分けて候補化する。
(a) が「編成そのまま・回数で吸収」、(b) が「編成組み替え」。(a) を上位に。
探索本体（buildBonusSweepTable / planFromReachablePtTable / frontier）は無改変で、
**呼び出し方（liveBonuses に現ボーナスだけ渡す等）と候補の詰め替え・並べ替え**で実現する。

## 禁じ手

- ON経路（マイセカイ利用時）の計算結果を変えない。`calculator.test.ts` / `liveAdjust.test.ts`
  の凍結テスト・ゴールデンは1文字も触らない。
- `planMultiLiveAdjustment` の frontier構築ループ・best選択、掃引ループ（liveAdjust 5.1/5.2）を
  改変しない。呼び出しと詰め替えだけ。
- 低LB・多本数・組み替え候補を**削除しない**（並べ替え・畳みは可）。
- マジックナンバー禁止。閾値・刻みは定数か既存関数から導出。
- 800行超のファイルを作らない（超えるなら分割）。
- 新しい「嘘の状態表示」を作らない（過去ラウンドで繰り返した失敗。トグル/選択が
  不適用に落ちたら必ず notice を出す）。

## 受け入れ条件

- `npx tsc --noEmit` exit 0 / `npx vitest run` 全通過 / `npm run build` 成功
- ON経路の凍結テスト・ゴールデンが無変更で通過
- 候補リストの並び順が「編成変更が小さい順（現ボーナス維持 → 下げ幅小 → 大）」であることのテスト
- 選択した候補が統合画像・合計に反映されることのテスト
- 397% のような大きい下げ幅の案が先頭に来ないこと（7,809 相当の入力で先頭が
  「編成そのまま・複数回」になることのテスト）
