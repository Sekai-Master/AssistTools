# ポイント調整アナライザー Step2（ライブ調整）出力の再設計ブリーフ

作成: 2026-07-23 / 起点: 2026-07-23 のイベント実戦運用（最終13位）で判明した問題

## 背景：なぜ今これをやるか

2026-07-23、実際のイベント終盤（残り3時間）でこのツールの想定用途をフルに使い、
Step2 の出力が **意思決定に使えない** ことが実運用で確認された。
R2/R3 で複数回プランに対応した結果、計算は正しいが提示が判断を助けていない。

## 診断（この改修の根拠。実装前に必ず読むこと）

### 1. パレート前線 `(回数, LB)` は、ほぼ全域が支配されている

現状の出力例（残 80,527 Pt、ボーナス990%）:

| | 回数 | LB合計 | 所要時間(実測ベース) |
|---|---|---|---|
| プラン1「回数最少」 | 2回 | 9 | 約7分 |
| プラン2 | 3回 | 8 | 約8分 |
| プラン3 | 10回 | 7 | 約30分 |
| プラン4 | 12回 | 6 | 約43分 |
| プラン5「LB最安」 | 37回 | 0 | 約138分 |

プラン1 を基準に差分を取ると:

| | 節約LB | 追加時間 | LBの価値(Pt換算) | その時間を周回に充てた価値 |
|---|---|---|---|---|
| プラン3 | 2 | +23分 | 16,890 | 約144万 |
| プラン5 | 9 | +131分 | 76,005 | 約820万 |

**調整ライブはソロ**（1本あたり数千〜数万Pt）だが、**周回はみんなでライブ**（1本12万Pt級）。
よって「LBを節約するために本数を増やす」は、その時間を周回に回した場合に常に負ける。

- イベント途中 → 機会費用で負ける
- イベント終盤 → そもそも時間が残っていない

**どちらの局面でも低LB・多本数プランは選ばれない。** 前線の下側は選択肢ではなくノイズ。

### 2. 回数は時間の代理指標として機能しない

基礎点が高い曲ほど長い（基礎点130=メルト182.1秒 / 基礎点100=独りんぼエンヴィー74.8秒）。
「回数最少」プランは1本あたりが最も長い。**回数を減らしても時間は減らない。**
`music_time` は `public/MusicDatas/transformedMusics.json` に既に存在するのに使われていない。

### 3. 主用途が埋没した

`projects/point-analyzer.md`（Nori のブレイン）が定義する主用途は
**「独りんぼエンヴィーをソロ・ライブボーナス0〜1消費で叩く端数調整」**、
利用者は **スマホでゲームと行き来しながら片手で使う**。

利用者層は2つに割れる:

| | 周回の焚き方 | 1回の獲得 | Step2 の残額 | 調整の形 |
|---|---|---|---|---|
| 上位・課金 | LB10固定 | 12万超 | 〜12万 | 複数本・大きい値 |
| 無〜微課金 | 3〜5焚きで微調整 | 小さい | 小さい | **エビ1〜2本・LB0〜1** |

R2/R3 は前者（例外側）に最適化し、後者（主用途）を「第1候補」の内側に埋めた。

### 4. スコア帯の実行可能性が計算の外にある

「スコア 700,000〜719,999」のような中間帯は、総合力が高いほど**意図的に抜く**必要があり難しい。
一方 `0〜19,999`（放置）や自己最高付近（全力）は容易。この難易度差が提示に現れていない。

### 5. 着地不能域（正しさの穴）

1本で作れる最小値は `calcLivePt(最小基礎点, bonus, 0, LB0)`。
ボーナス990%・基礎点100なら **1,090**。したがって:

- 残額 1,089 以下 → **原理的に着地不能**
- 残額 1,090〜6,807 → **3本使っても作れない値が200個以上**（例 1,091〜1,099、2,202〜2,210）
- 残額 6,808 以上 → 3本以内で必ず到達可能

閾値はボーナス依存なので**動的に計算すること**（上記数値は990%時の実測値）。
「1ptでもズレたら失敗」がこのツールの価値の根なので、これは機能ではなく**正しさの欠落**。

### 6. ライブボーナス効率の崖（2024-09-28 改定）

`calcLivePt.ts` の `LIVE_BONUS_MULTIPLIERS` より、1LBあたり倍率:

| 焚き | 旧倍率 | 旧効率 | 新倍率 | 新効率 |
|---|---|---|---|---|
| 3 | 15 | 5.00 | 15 | 5.00 |
| 4 | 19 | 4.75 | **20** | **5.00** |
| 5 | 23 | 4.60 | **25** | **5.00** |
| 6 | 26 | 4.33 | 27 | 4.50 |

**旧仕様は3焚きの直後に効率が落ちた。新仕様は5焚きまで横ばい。**
「3焚きまで」という旧仕様時代の最適運用が今も広く信じられているが、
現在は5焚きまで同効率のため、3焚きで止めると**本数（＝時間）だけ余計に払う**。

## 勝利条件

1. **残り時間8分・スマホ片手・イベント終盤という最悪条件で、迷わず1つ選べる**
2. 支配されている選択肢が、支配されていない選択肢と同じ重みで並んでいない
3. 着地不能な残額を、着地不能と分かる形で警告する
4. 無課金運用（低焚き・小残額）が主役として扱われている
5. **既存の計算結果（厳密一致・回数最小性）を1ptも壊さない**

### 採点基準

- 判断可能性（時間・LB・実行難易度が同一画面で比較できるか）
- 主用途への適合（エビ・低LB・小残額のケースが最短動線か）
- 正しさ（着地不能域の検知、厳密一致の維持）
- スマホ片手での操作量（スクロール・タップ数）

### 禁じ手

- **ON経路（マイセカイ利用時）の挙動を変えないこと。** 凍結テストとゴールデンは1文字も触らない
- 既存の厳密一致・回数最小性の保証を弱めないこと
- 低LB・多本数プランを**削除**しないこと（畳むのは可、消すのは不可。終盤以外・LB枯渇時に成立しうる）
- ユーザーに「時間とLBのどちらが大事か」を毎回選ばせないこと（軸の切り替えUIは不採用と結論済み）
- マジックナンバー禁止。閾値・倍率は既存定数か `calcLivePt` から導出する

## 実装内容

### P0

1. **所要時間の算出と表示**
   - 1本の所要 = `music_time` + オーバーヘッド定数（実測 **47秒**。定数として定義しコメントで根拠を書く）
   - 全プランに「約N分」を併記
   - `music_time` は楽曲データに存在。型・ロード経路を確認して配線する

2. **出力構造の作り直し**
   ```
   ② ライブ調整 — 80,527 Pt
     ▸ 2回 / 約7分 / 編成変更なし        ← 主役。大きく1案だけ
         メルト（182秒）              7焚き  スコア 1,040,000〜1,059,999   62,437
         とても素敵な六月でした（154秒） 2焚き  スコア   700,000〜  719,999   18,090
     ▼ 同じ2回で組み替える（LB内訳違い N件）      ← 畳む
     ▼ 本数を増やしてLBを節約（非推奨・+23分〜）  ← 畳む。時間差を明示
   ```
   - LB の選択肢は**同一本数の中でのみ**提示する
   - 多本数プランは残すが「非推奨」＋追加時間を明示して畳む

3. **曲名のインライン表示**
   - 「基礎点130」で止めず「メルト（182秒）」まで出す
   - 現状の「プランを選ぶと曲候補が下に出る」2段階を廃す（片手スマホでスクロールが増える）
   - 同一基礎点の代替曲は短い順に2〜3件を副次表示

### P1

4. **スコア帯の実行難易度バッジ**
   - `0〜19,999` → **放置**
   - ユーザー設定のスコア上限付近 → **全力**
   - 中間帯 → **狙い撃ち**

5. **編成変更なしバッジ**をプラン単位に（ヘッダー注記では届いていない）

6. **同一曲縛りトグル**（＝エビ詰めモードの主役復帰）
   - 曲を探す手間が消えることに独立した価値がある

### P2

7. **着地不能域の警告**
   - 到達可能な最小値をボーナスから動的計算し、残額がそれ未満なら明示的に「着地不能」
   - 穴の多い帯（最小値〜安全域）では「解が0件なら着地できない」旨を警告
   - 可能なら Step1 側で「あと1回周回すると着地不能域に入る」事前警告

8. **LB効率の注記**（周回設定の近く）
   - 「5焚きまでは1LBあたりの効率が同じ（2024-09-28改定）。3焚きで止めると本数が増えるぶん時間を損します」

## 受け入れ条件

- `npx tsc --noEmit` exit 0
- `npx vitest run` 全通過（既存152件＋新規を含む）
- `npm run build` 成功
- **ON経路の凍結テスト・ゴールデンが無変更で通過**
- 新規テスト:
  - 所要時間の算出が `music_time + 47秒 × 本数` と一致
  - 同一本数内でのみ LB 内訳を出していること
  - 着地不能域の判定（ボーナスを変えて閾値が動くこと）
  - 既存の厳密一致・回数最小性が維持されていること
