# マイセカイ リアクション図鑑（/mysekai）

キャラが反応する家具をキャラ別に一覧するツール。2026-08-17 追加（v1.13.0）。

## なぜ作ったか

ゲーム内にも「リアクションあり」の絞り込みはあるが、**自分が設計図を持っている家具しか表示されない**。
そのため次の2つができなかった。

1. まだ持っていない家具を知る（「このキャラを喜ばせる家具が他にもあるのか」が分からない）
2. 他人のマイセカイへ模写しに行く計画を立てる（そもそも対象が見えない）

加えて、マイセカイを開いている端末では同時に一覧を見られない。別端末で開けることに実用価値がある。

## 「反応」は3種類あり、別物

重なるが一致しない。A∪B∪C=456（家具全1,518件中）。

| 種別 | 件数 | 判定 |
|---|---|---|
| A. キャラアクション | 182 | `mysekaiFixtures.isGameCharacterAction` |
| B. 固有会話 | 369 | 会話の発火条件が `mysekai_fixture_id`（会話5,724本） |
| C. 好み | 279 | キャラ×`positive` の家具グループ |

### ⚠️ 混ぜてはいけないもの（実装レビューで実際に壊れた箇所）

**1. 無関心（normal）を好みと一緒にしない。**
`mysekaiCharacterTalkFixtureCommons` は `positive`（好み）と `normal`（無関心）の2種類を持つ。
当初は両方を「反応」として扱っていたが、normal はほぼ全キャラ×ほぼ全家具に付くため、
**26人の絞り込み結果がほぼ同一になった**（実測 平均 Jaccard 0.957、会話数順の上位10件が26人全員で完全一致）。
normal は関心の証拠ではないので**出力しない**。除いた結果 Jaccard 0.654、上位10件は26人とも別の並びになった。

**2. 家具全体の会話数をキャラ別の画面に出さない。**
`talkCount` は家具に紐づく会話パターンの総数。キャラを選んだ画面でそのまま出すと
**実数の19倍**になる（星乃一歌で 4,205 本と表示・実際は 220 本）。
`tk` にキャラ別の本数を持たせ、`talksOf(fixture, charId)` で出し分ける。並べ替えも同じ値を使う。

**3. `isGameCharacterAction` をキャラ別に見せない。**
これは家具単位のフラグで**誰が動くかを持たない**。charSet で代用したところ、
どのキャラを選んでも出てこない家具が28件（会話も好みも無いが動く家具）、
逆に会話も好みも無いのに出る偽陽性も発生した。**キャラ選択中は action で絞らない。**

**4. ミクの「好み」は5つのセカイぶんの合成。**
好みは `gameCharacterUnit` 単位で定義されており、**ミクだけ5ユニットぶんの行を持つ**
（他のバーチャル・シンガーは1ユニットぶんのみ、しかも VS 版ではなくユニット版）。
キャラ単位に潰すのは重複排除ではなく**別プロファイルの合成**で、和集合204件のうち
5つ全部に共通なのは28件だけ。さらに合成すると同じキャラが positive と normal の
両方に入る家具が128件でき、画面が「お気に入り」と誤って断言する。
→ **positive を優先**して normal から除き、`multiUnitLikes` に記録して画面に注記を出す。

## B（固有会話）の結合経路

ここが実装の肝。`scripts/lib/deriveMysekaiData.mjs` が担当する。

```
mysekaiCharacterTalks (7,281)
  ├─ mysekaiCharacterTalkConditionGroupId
  │    └→ mysekaiCharacterTalkConditionGroups （groupId でまとまる）
  │         └→ mysekaiCharacterTalkConditions
  │              └ type === "mysekai_fixture_id" の typeValue が家具ID
  └─ mysekaiGameCharacterUnitGroupId
       └→ mysekaiGameCharacterUnitGroups （1〜5人の組）
            └→ gameCharacterUnits → gameCharacters
```

**踏みやすい罠が2つある。**

1. **会話は1〜5人のグループで発生する**（実測: 1人56 / 2人240 / 3人620 / 4人1065 / 5人1266グループ）。
   参加者を全員 `talkChars` に展開しないと、「2人会話にしか出ないキャラ」が絞り込みから丸ごと漏れる
2. **1人のキャラが複数の `gameCharacterUnit` を持つ**（ミクは VIRTUAL SINGER と各ユニットぶん）。
   潰さないと同じ人が複数回出る

条件グループは AND で、家具以外の条件（読了エピソード58 / 天候17 / 訪問回数10）も同じ表に入っている。
家具条件だけを拾い、他は無視している。

## ⚠️ この表は未公開判定ができない

**家具マスタは日付欄を持たない**（全26キーを確認済み・2026-08-17）。
`mysekaiBlueprintTerms` は期間限定配布の125件しか持たず、全1,462件の設計図を覆えない。

カード・イベント側は `publishedAt` / `startAt` があるので `published = at <= now` で切れ、
`deriveCardData.mjs` の `auditLeaks()` が未公開データの痕跡を検算して**書き出しを止める**。
**家具ではこれが原理的に書けない。**

`mysekaiGates` について「日付欄を持たないので未公開判定が効かない。名前とアセット名は出さない」
という判断が既にあるが、家具一覧では名前を出さないと成立しないため、代わりに次の緩和策を採った。

- **画面の既定フィルタを「反応がある家具だけ」にする**（既定表示は456件。全1,518件は明示操作で開く）。
  反応データは実装とセットで作られるため、実装前の家具が既定で目に入りにくい。
  実測でも新しい家具ほど反応を持たない（id 末尾20件で反応ありは2件だけ、反応あり456件の id 中央値は459）
- 生成時に**前回出力との差分件数をログに出す**。一度に50件以上増えた回は警告を出す
- 将来マスタに `releaseAt` 相当が入ったら `deriveMysekaiData.mjs` に published 判定を足すこと

Nori 判断（2026-08-17）で全件出力としている。網羅性を優先した結果であり、
既存の「公式が公開していない情報を出力に残さない」方針とは緊張関係にある。**方針を変えるときはここを読むこと。**

## 取得元は GitHub Pages（既存2スクリプトと違う）

```js
const BASE = "https://sekai-world.github.io/sekai-master-db-diff";
```

既存の `refresh-music-data.js` / `refresh-card-data.mjs` は `raw.githubusercontent.com` を使っているが、
マイセカイ系は必要な表が12本あり、**raw を連続で叩くと 429 Too Many Requests に落ちる**ことを実測した。
同じ内容が GitHub Pages 経由なら制限に当たらない。既存2本は動いているので移していない。

## 会話本文は扱わない / 家具画像は自前配信する

- **会話本文**: `mysekaiCharacterTalks` が持つのは lua スクリプト名だけ。
  `storage.sekai.best` を `.lua/.txt/.asset/.bytes` の4拡張子で試して全404（同ホストの楽曲ジャケットは200なので未配信）。
  Nori 判断でネタバレ回避のため扱わない
- **家具画像**: サムネイルは存在する。正本は sekai-viewer の `src/utils/mysekaiFixtureUtils.ts`。

```
通常家具            mysekai/thumbnail/fixture/{assetbundleName}_1.webp
内装(surface_appearance)  mysekai/thumbnail/surface_appearance/{ab}/tex_{ab}_{layout}_1.png
```

  152×152・アルファ付き。**Referer 付きは403**で弾かれるので、立ち絵と同じく
  ビルド時に落として自前配信する（迂回しない）。

  ⚠️ **内装は assetbundleName が壁紙と床で共通**。保存名を assetbundleName だけにすると
  後勝ちで上書きされ、片方が別物の絵になる（実測31種類・のべ77件で発生）。
  保存名には向きを含めること（`{ab}_{layout}`）。`deriveMysekaiData.mjs` の `thumbName()` が担当。

  なお苗4件・種15件が同じ画像を共有するが、これは**上流が正当に共有しているもの**
  （植えた直後は見た目が同じ）。「バラの種/赤」と「バラの種/青」は一覧では名前でしか区別できない。

## 配信データ

`public/MysekaiDatas/fixtures.json`（412KB / **brotli 32KB**）とサムネイル 1,501枚（5.9MB）。
この画面でしか使わないので独立させている。

転送量を優先してキーを短くし、空の項目は落としてある。画面側は `src/pages/mysekai/lib/types.ts` の
`normalize()` で読みやすい形に戻す（「無ければ既定値」を1箇所に閉じ込める）。

| 短縮キー | 意味 |
|---|---|
| `pr` | 読み（名前と同じなら省略） |
| `ty` / `st` / `ly` | 種別 / 設置場所 / 向き。`vocab` の添字 |
| `sz` | `[幅, 奥行き, 高さ]` |
| `co` | 設置コスト |
| `sk` | 模写可否。**3値**: true(可) / false(不可) / 省略(設計図が存在しない) |
| `ac` | キャラアクション（true のときだけ 1） |
| `tc` | 固有会話に登場するキャラID配列 |
| `tk` | `tc` と同じ並びで、そのキャラの会話本数 |
| `ts` | 同じ並びで、そのうち**ひとりで喋る**本数（0 なら誰かと一緒に居ないと始まらない） |
| `tn` | 家具全体の会話本数 |
| `tp` | 会話する最大人数（2以上のときだけ持つ） |
| `lc` | 好み（positive）のキャラID配列 |
| `pt` | 会話が起きる顔ぶれ（キャラIDの配列の配列）。**回収チェックの単位** |
| `im` | サムネイルのファイル名。内装は向きを含む（後述） |

**`sk` の3値を混ぜないこと。** 「模写不可」と「設計図が存在しない」は入手経路の話として別物で、
どちらも模写では手に入らないが、後者はイベント配布などの固定設置物を含む。

**`craftTargetId` の名前空間に注意。** `mysekai_fixture` と **`mysekai_canvas` は家具IDを共有する**
（canvas の 439〜444 は家具表の `type === "canvas"` と一致し、全て模写可）。
当初 canvas を弾いていたため壁掛けキャンバス6件が「設計図なし」と誤表示され、模写フィルタから消えていた。
一方 `mysekai_tool` の 1〜10 は**道具側の別の名前空間**なので必ず除外する。

### ソロ会話と複数人会話（`ts` / `tp`）

会話は1〜5人のグループで発生する。**ひとりで喋る会話と、誰かと居ないと始まらない会話は
家具を置く動機がまるで違う**（後者はその子ひとりを訪ねても何も起きない）。実測の内訳:

| | 件数 |
|---|---|
| 全員がソロ会話を持つ | 315 |
| **誰もソロ会話を持たない**（ユニットのソファ等） | **16** |
| キャラによって分かれる | 38 |

最大人数の分布は 1人=269 / 2人=93 / 3人=1 / 4人=6。画面では「揃うと」バッジで示す。

## 検証

```bash
npm run data:refresh-mysekai   # 生成。件数が実測値と合うか見る
npm test                       # derive 23 / filter 28 / storage 18 / types 15 / 実データ検算 12
```

生成時に出る件数が次と一致すれば結合は正しい（2026-08-17 時点）。

```
家具 1518件 / 反応あり 456件（固有会話 369 / キャラ動作 182 / 好み 279）
会話 5724本 / 模写可 706件 / キャラ 26人
```

ずれたらマスタ側が変わったか、結合を壊している。差分ログを見て切り分ける。

### 件数が合っていても壊れていることがある

初回実装は上の件数を**全て正しく再現していたが、キャラ絞り込みが機能していなかった**
（無関心を混ぜたため26人の結果が Jaccard 0.957 でほぼ同一）。
件数は「取りこぼしていないこと」しか保証せず、「混ぜすぎていないこと」を見ない。
結合を触ったら、件数だけでなく**キャラ間で結果が実際に違うか**を確かめること。

```bash
# キャラ絞り込みが効いているかの目安（平均 Jaccard が 0.7 を超えたら疑う）
node -e '
const d=require("./public/MysekaiDatas/fixtures.json");
const cs=(f)=>new Set([...(f.tc||[]),...(f.lc||[])]);
const r=Object.fromEntries(d.characters.map(c=>[c.id,
  new Set(d.fixtures.filter(f=>(f.tn||f.ac||f.lc)&&cs(f).has(c.id)).map(f=>f.id))]));
const ids=Object.keys(r), j=[];
for(let i=0;i<ids.length;i++)for(let k=i+1;k<ids.length;k++){
  const a=r[ids[i]],b=r[ids[k]];
  j.push([...a].filter(x=>b.has(x)).length/new Set([...a,...b]).size);}
console.log("平均 Jaccard:", (j.reduce((x,y)=>x+y)/j.length).toFixed(3));'
```
