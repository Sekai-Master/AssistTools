## 2. モデル（`share-median-v1`）

`終値予測 = 現在の実測ボーダー ÷ シェア表(期間, 順位帯, 経過率)`。シェア＝「過去のイベントで、その経過率の時点に終値の何割まで積み上がっていたか」の中央値。水準（イベントの熱さ）は現在値がすでに運んでいるので、過去から借りるのは**形だけ**。根拠と検証の経緯は brain の `log/2026-09-02-border-prediction-system.md`。

- 経過率の格子は 0.02 刻み（51点）。サンプルの空白が **2時間を超える区間は補間しない**（216 で sekai.best が 23時間止まり、補間した点の誤差が壊れた）
- 誤差の定義は `予測 ÷ 実測終値 − 1`（マイナス＝低く外した）

### 2.1 自己改善（王者と挑戦者）

候補は4つ。どれも「対象イベントの開始前に終わったイベントだけ」で表を作る（リークは `test/model.test.ts` で落ちることを確認済み）。

| 候補 | プール |
|---|---|
| `same_all` | 同じ期間の全履歴（標本3件未満なら全マラソン）。旧 v0 と同じ |
| `same_recent8` | 同じ期間の直近8件 |
| `all_recent12` | 期間を問わず直近12件 |
| `same_all_debias5` | `same_all` を、直近5件で出ていた偏り（誤差の中央値）で補正 |

1. 終わったマラソンを時系列順に並べ、各候補で**前向き検証**（その時点までのデータだけで当てる）
2. 1イベントの点数＝経過率 0.40〜0.96 の |誤差| の中央値。直近8件の平均で比べる
3. 挑戦者が王者より **5%以上**良いときだけ入れ替える（ヒステリシス）。**順位帯ごとに別々に選ぶ**
4. 帯＝王者の直近20件の誤差（経過率 ±0.04 の範囲）の分位点。非対称のまま使う（系統的に低く外す帯は、帯が上に伸びる）。**裾の広さは順位帯ごとに自動で選ぶ**: 10〜90% から 2.5〜97.5% までの候補のうち、前向き検証で実際に **8割以上が入った中でいちばん狭いもの**。固定の10〜90%では実際には73〜80%しか入らず、「8割の幅」が言い過ぎだった（2026-09-30、72件で実測）
5. 表に出すのは開始6時間（150h で経過率 0.04）から。帯の幅で**確度**を付ける: 幅10ポイント以内＝高（±5%くらい）、30ポイント以内＝中（±15%くらい）、それより広い＝目安。80ポイントを超える帯は幅として意味が無いので出さない（予測は記録する）。帯の裾は**序盤（経過0.3まで）と中盤以降で別々に**選ぶ（序盤は外れ方がずっと大きく、同じ裾だと片方だけ当たり率が足りなくなる）
   - 序盤の表は §2.1.2 の差し替え（blend）で作り直すことがある。下の数字は差し替えを入れる前のもの
   - 序盤の実力（過去57〜61回・前向き）: 開始6時間で |誤差| の中央 8〜12%、実測を見ずに「最近の終値の中央値」を答えるだけの予測（21〜32%）の約3分の1。6〜24時間はほとんど締まらず、締まるのは48時間あたりから（2026-09-30 実測）

### 2.1.1 投稿の節目

開始24時間（序盤の目安）・経過50%・経過85% の3回と、終了後の答え合わせ。節目を経過率で 0.05 以上過ぎてから気づいた回（途中から動き出した等）は、その節目のポストを出さない。ポストには画像を作るためのデータ（`PostPayload`、D1 の kv に `post:{id}`）を添える。画像は sekaimaster-bot が作り、文字だけの `text` は画像の代替テキストと、画像が作れなかったときの控えに使う。

答え合わせの後に積む一言解説（`<回>:insight`、`scripts/claude/border-insight-run.ts`）には `{ kind: 'insight', eventId, replyTo: '<回>:result' }` を添える（2026-10-26）。Bot はこれを見て、補足を答え合わせへの返信（X のツリー・Discord の返信）にし、推移のグラフ（`/api/border/events/{id}/history` から描く 6:5 の1枚）を付ける。返信先の投稿 ID は Bot が自分の DB に覚えるので、Worker は変わらない。古い Bot は知らない kind を文字だけ・単独で送り、新しい Bot は payload の無い insight も返信として扱うので、どちらを先に入れても壊れない。詳細は sekaimaster-bot の `docs/border-relay.md`。
6. 版の名前は `share-median-v1@e{学習に入れた最後のイベント}-{表の中身のハッシュ}`。学習データが同じでもロジックを直せば別の版になって切り替わる。予測ログに版を必ず残す

**人が方向の補正を足す枠は作らない**（215 で人の下方修正が精度を下げた。brain log §11.2②）。補正は「補正つき候補」が前向き検証で勝ったときだけ自動で入る。

### 2.1.2 序盤の差し替え（blend、2026-10-26）

長さの違う回を経過の割合でそろえると、序盤の伸び方がずれる（221 = 102h で 150h の回の形を借りて大きく外した）。そこで序盤だけ、全マラソンを「開始からの経過時間」と「終了までの残り時間」の両方でそろえて混ぜた表に差し替える（2026-10-25 Nori「それで作ってよいです」）。

`share(p) = (1 − p) × 中央値[経過時間でそろえた share] + p × 中央値[残り時間でそろえた share]`

1. 切り替え点の候補は経過率 20・30・40%。その手前だけ blend にし、それ以降は王者の表のまま。blend の値が出ない点（そろえた先が 0〜1 の外で3件そろわない）も王者の表のまま
2. **順位ごとに前向き検証で選ぶ**（`fit.ts` の `walkEarlyBlend`）。各回を「その回より前の回だけで選んだ切り替え点」で当て、直近20件の序盤（経過 4〜38%）の |誤差| の中央値の平均で比べる。現行（差し替えなし）より **5%以上**良い候補があるときだけ入れ替える（王者と同じヒステリシス）。採点できた回が10件未満のうちは差し替えない。最初は差し替えなしから始める
3. 王者の採点（経過 0.40〜0.96）には触れない。当たり率・要約の誤差・帯の裾の選択は、各回を**その回の時点で選んでいた切り替え点**で差し替えた誤差で作る（前向きのまま）。帯の分位点だけは、全回を最後に選んだ切り替え点で差し替えた誤差で作る（これから出す予測と同じ作り方の誤差の分布）
4. 焼き込むのは期間ごとの表（`tables["150"]` など）と、標本1〜2件の長さの表（`tables["thin:102"]` など、§2.1.3）の借り先の部分だけ。学習に無い長さ用の `all`・`far_long`・`far_short` は、当てる回の長さがわからないので差し替えない。どこまで差し替えたかは版の `ranks[*].earlyBlendUntil` と要約の `earlyBlend` に残る
5. 実績（2026-10-26、125〜221 の75回・前向き。切り替え点も各回の時点で選んだもの）: 全順位をまとめた |誤差| の中央値は 経過4〜8% で 8.2→7.4%、10〜18% で 7.2→6.8%、20〜28% で 6.1→5.8%、30〜38% で 5.1→5.0%。100位は現行に勝てず差し替えなし、ほかの5順位は 40% まで。50位の 10〜18% は 9.4→10.3% と悪くなる（切り替え点1つでは区間ごとに外せない）。221 の 1000位の外れは、経過4〜8% の |誤差| が 38.1→28.8% までしか縮まらない
6. 切り替え点で表がつながっていないので、そこで予測が段差になる（102h の 200位で約 −9%）。blend の値が出ない点（1 の後半）が区間の途中にあると、そこにも段差ができる

### 2.1.3 学習に少ない長さ（参考値、2026-10-25〜26）

長さ（時間）ごとの表を作るのは、学習に**3件以上**ある長さだけ（`model.knownDurations`。#171）。それ以外の長さは Worker が「参考値」として出す: 予測に `extrapolatedFrom`（借りた先の長さ）を付け、帯を `FAR_BAND_FACTOR`（1.5）倍に広げ、帯がどれだけ狭くても確度は「目安」までにする（221 = 102h で終盤に「確度 高」と出て、1000位は開始24時間の予測 約1,640万を実測が上回った。#154）。サイト・投稿文・Bot の画像は `extrapolatedFrom` を見て「参考値」と書く。

| 学習にある同じ長さの回 | 使う表（`chooseTable`） |
|---|---|
| 3件以上 | `tables["<長さ>"]`（王者の候補の表。序盤は §2.1.2） |
| 1〜2件 | `tables["thin:<長さ>"]` = 0.3 × 同じ長さの直近の回の share ＋ 0.7 × 下の行の借り先（序盤は §2.1.2 と同じ切り替え点で blend に差し替え）。`model.thinDurations` に長さ・件数・混ぜた回を残す。札の数字（`extrapolatedFrom`）は3件以上の長さのうちいちばん近いもの |
| 0件 | 最短より短ければ `far_short`、最長より長ければ `far_long`（その端の長さの全履歴の中央値）、その間なら `all` |

- 重み 0.3（`THIN_WEIGHT`、`model.ts`）の根拠（2026-10-26、`border-research/experiments/thin-duration-2.md`。124 以降のマラソン・前向き）: 前例が3件以上ある長さの回でも、同じ長さの前例を直近の1件だけ残して「2回目」とみなした 57 回 × 6順位で、全順位の |誤差| の中央値が 経過4〜8% で 7.9→7.0%、10〜18% で 7.5→6.5%、20〜28% で 5.9→6.0%、30〜48% で 5.5→5.0%、50〜70% で 4.2→3.8%、72〜96% で 2.7→2.6%（借り先→thin）。90% 点もほぼ同じか狭い。直近の1件を**そのまま**使うとどの区間も借り先より悪く（4〜8% で 9.1%）、重み 0.5 以上は序盤で悪くなる。前例をいちばん古い1件だけ残しても 0.3 は借り先と同じか少し良い
- 本当に「その長さの2〜3回目」だった回は 124 以降に5回しかなく（135・136・138・150・153、学習7〜23回の時点）、そこでは借り先と thin の差ははっきりしない（4〜8% で 7.3→8.3%、20〜28% で 7.6→6.5%）。決め手は上の 57 回の再現
- 終盤だけ重みを抜く案（経過 50% から 80% にかけて 0 へ）は、前例と当てる回の終了の曜日が違う回でも良くならなかったので採らない。日曜終了の回は終盤の積みが平日終了より1割ほど大きい（1000位の終了前12時間の倍率 3.31 対 2.96、`thin-duration-sunday.md`）が、221 の 500・1000位の終盤の積みは、長さで割り戻すと日曜終了の回の中でむしろ小さい（どの回より小さいか下から1割以内）
- ワールドリンクの形は使わない。72h の WL（218）は伸びがほぼ直線で終盤の追い込みが小さく、221 を当てると 1000位の経過50% で −32%（150h の借り先は −19%）。長い WL は章ごとの段差がある（`thin-duration-wl.md`）
- 古い Worker は `thin:` の鍵を読まない（数字だけの鍵＝完全一致に当たらないので借り先のまま）。thin を効かせるには Worker のデプロイが要る

### 2.1.4 5分ごとの見回りが積む投稿（日報・終了前の追い込み・開始直前の告知）

Cron（`*/5 * * * *`）が、時刻で決まる投稿を積む。どれも画像は sekaimaster-bot が描く（6:5）。

| 投稿 | いつ | 中身 | 場所 |
|---|---|---|---|
| 日報 | 毎日21時台（21:03 の点が入ったら）。**終了の日の21時は出さない**（終了の後なので。`dailyTimes` は終了より前の21時だけ） | 6順位の いま・直近24時間・直近1時間・歴代ペース・最終予測 | `src/daily.ts` |
| 開始直前の告知（2026-10-26。Nori「イベント開始直前のツイートが何かしらあってもいいかもね」） | 開始75分前〜15分前の見回りで、**開始15分前の時刻（payload の `postAt`）** を付けて積む。Bot がその時刻ちょうどに出す（歴代ボーダーと同じしくみ）。15分前を過ぎてから気づいた回は積まない | 新しい回の名前・素材名・期間・長さ、同じ種別（Memories は見分ける）で同じ長さの直近の回の6順位の終値（無ければ前例なし）、最初の予測の時刻（マラソンだけ）と日報の時刻。本文は手で出した 222 の文面が基準で、Bot が X にだけハッシュタグを足す（本文は重み 244 以内） | `src/start.ts` |

- マラソン・チアフルだけ（ワールドリンクは出さない）。同じ回に2回は積まない（id が `{id}:daily:{日}`・`{id}:spurt`・`{id}:start`）
- **開始の告知は公開前の情報を出さない**: 使うのはマスタの名前・期間・素材名と歴代の表だけ。出るのは開始15分前で、ゲーム内の告知（マスタの `eventOnlyComponentDisplayStartAt`。219〜222 は開始3時間前）より後。積むのも開始75分前から
- **開始の告知は、その回が開始75分前までに events に入っていることが前提**。events に入る道は2つ: 解析ジョブ（1日2回、10:47・22:47 ごろ）がマスタ（sekai-master-db-diff の events.json）を `PUT /admin/events` で入れる／Worker が開催していない間に6時間に1回サイトの bonuses.json を読む。マスタに新しい回が載るのは開始の14〜72時間前（216〜222 の実測。222 は前日 21:00・221 と 220 は前日 15:00・217 は当日 0:00 で開始の15時間前）で、解析ジョブの次の回で入るので、7回とも開始の4時間以上前に入る計算。**当日0時ごろに載る回（217・216）は、解析ジョブの 10:47 の1回が止まる・大きく遅れるだけで落ちうる**（その回の告知だけが出ない。ほかは壊れない。GitHub の定時実行は遅れや抜けがある）。手当ての案は PR（AssistTools の開始の告知の PR）に書いた
- **入れる順番は Bot（sekaimaster-bot）が先**。古い Bot は `start` を読めず時刻付きにもならないので、Worker を先に入れると開始の約1時間前に画像なしの「まもなく」が出る

### 2.2 対象外

openssl rand -hex 32 | tr -d '

## 5. 運用

- **見る場所**: `https://sekaimaster.pages.dev/api/border/current`（最新の予測）、Actions の実行結果のサマリ（版・候補・誤差・帯の的中率）、`npx wrangler tail sekaimaster-border`
- **sekai.best が止まったとき**: 同じ `sampleAt` が返ってくる回は予測を積み増さない（`stale`）。画面は90分以上止まると注意を出す
- **投稿**: Worker と解析ジョブは D1 の `posts` に積むだけ。**送るかどうかは sekaimaster-bot 側の設定**（X・Discord それぞれ別スイッチ）。古い投稿は Bot 側で捨てる
- **モデルを手で戻したい**: `models` 表の `active` を付け替える（版は消さない）
- **表の定義を変えたとき（migrations/ に足したとき）**: デプロイの前に `npx wrangler d1 migrations apply sekaimaster-border --remote`。0002（イベントの素材名の列）は 2026-10-25 に追加。先にデプロイすると、日程の取り込みが「asset という列が無い」で失敗する
- **歴代の表の見回りのログ**: `npx wrangler tail sekaimaster-border` で `finals {"status":"added",...}`（足した）・`waiting`（確定後の点を待っている）。ふだんの回はログを出さない

## 7. 判断の記録

- **Actions で取得して JSON をコミットする案は採らない**: 30分ごとのコミットは Pages のビルド（500回/月・同時1本）を食い潰し、コードのデプロイを詰まらせる
- **画面は Pages Functions 経由で読む**: workers.dev を直接叩かせると、プライバシーポリシー第5項「ページを開いただけで外部のサーバーに接続しない」が嘘になる
- **学習は Worker でやらない**: 無料枠の CPU は Cron でも 10ms。前向き検証は数万回の中央値計算になる
- **KV ではなく D1**: 予測ログを引いて採点し直すので、問い合わせのできる置き場所が要る
