# バージョン管理とリリース手順

Sekai-Master のバージョンの決め方、更新履歴の書き方、リリースのやり方。**リリースするときは必ずこのページを開いて上からなぞる。**

## 前提: 版は2層ある

このサイトは「アプリ」と「ゲームデータ」が別々の速さで動く。1つの番号にまとめると必ず嘘になるので、最初から分けてある。

| 層 | 何を表すか | どこで動くか | どこに出るか |
|---|---|---|---|
| **アプリの版** | 画面・計算・機能そのものの変更 | 人がリリースしたとき | フッターの `v1.9.0` / 更新履歴ページ |
| **データの鮮度** | カード・イベント・楽曲データの取り込み日 | 毎日の自動更新（GitHub Actions） | フッターの「データ更新 2026-08-04」 |

**データの自動更新でアプリの版は上げない。** 毎日 minor が上がるバージョンには意味が無いし、更新履歴が `chore(data)` で埋まって読めなくなる。逆に、データ更新が本番に届いているかはフッターの日付で判断できる（実際、2026-08-03 にはこれが止まっていた）。

データの鮮度は `public/CardDatas/cards.json` の `generatedAt` をビルド時に読んで表示している（`vite.config.ts`）。手で持ち回る値ではない。

## アプリの版の付け方（セマンティック バージョニング）

`MAJOR.MINOR.PATCH`。判断に迷ったら「**使っている人の手元で何が壊れるか**」で決める。

| 上げる桁 | 条件 | 例 |
|---|---|---|
| **MAJOR** | 利用者の手元にあるものが壊れる | 保存データの形式を変えて過去のバックアップが読めなくなる／ツールを削除する／URL を変える |
| **MINOR** | できることが増える・変わる | ツールの追加／機能の追加／計算モデルの入れ替え／**利用規約・プライバシーポリシーの改訂** |
| **PATCH** | 直しただけ | 計算の不具合修正／文言・見た目の調整／性能改善 |

- 規約・ポリシーの改訂を PATCH にしないこと。**情報の扱いが変わる変更は利用者に伝わる必要がある**ので、更新履歴に載る MINOR 以上として扱う。
- リリースせずに main へ積んだ変更は、次のリリースにまとめて載る。1コミット1バージョンにはしない。

## 正本はどこか

| もの | 正本 | 備考 |
|---|---|---|
| 版の番号 | `package.json` の `version` | ビルド時にフッターへ差し込まれる |
| 更新履歴 | `CHANGELOG.md` | 更新履歴ページはこれを解析して描画する。二重管理はしない |
| 規約・ポリシーの日付 | `src/lib/site.ts` の `LEGAL_*_DATE` | |
| 窓口・サイト名 | `src/lib/site.ts` | 規約・ポリシー・フッターが全部ここを見る |

**`package.json` の version と `CHANGELOG.md` の先頭の版が一致しないとテストが落ちる**（`src/pages/legal/changelogParser.test.ts`）。片方だけ上げる事故は CI で止まる。

## CHANGELOG.md の書き方

```md
## [1.9.0] - 2026-08-04

（任意）この版全体の説明。1〜2文。

### 追加
- 使う人から見て何ができるようになったか

### 変更
- 何がどう変わったか

### 修正
- 何が直ったか
```

- **見出しの形を崩さない。** `## [版] - 日付` と `### 見出し` を解析してページを作っているので、形が違うとその版が丸ごとページから消える（テストで検出される）。
- 日付は **JST の日付**。
- 見出しは「追加」「変更」「修正」を使う。他の語を書いても表示はされるが、色は付かない。
- **開発者向けの言葉で書かない。** `feat(deck): ...` をそのまま貼らない。「編成ビルダーで、カードを編成に入れずに『持っている』だけ登録できるようになりました」のように、使う人から見た違いを書く。
- **内部だけの変更は載せない。** リファクタ・テスト追加・CI の調整は履歴に出さない（コミット履歴を見ればよい）。

## リリース手順

```bash
# 1. main が最新で、CI が緑であることを確認する
git switch main && git pull

# 2. CHANGELOG.md の先頭に新しい版を書く（上の書式）

# 3. package.json の version を同じ番号にする
npm version 1.9.0 --no-git-tag-version

# 4. 番号と履歴が一致していること・全部通ることを確認する
npm test && npm run build && npm run lint

# 5. コミットして push（CI が通れば Cloudflare Pages へ自動デプロイ）
git add CHANGELOG.md package.json package-lock.json
git commit -m "chore(release): v1.9.0"
git push

# 6. タグを打つ
git tag v1.9.0 && git push origin v1.9.0

# 7. GitHub Release を作る（CHANGELOG の該当節をそのまま貼る）
gh release create v1.9.0 --title "v1.9.0" --notes "..."
```

### 8. 出たことを確認する

- <https://sekaimaster.pages.dev/changelog> に新しい版が出ているか
- フッターの `v` が上がっているか
- フッターの「データ更新」が今日か（止まっていたらデータ更新のワークフローを見る）

### 9. 告知する

公式 X（[@pj_Sekai_master](https://x.com/pj_Sekai_master)）で告知する。**文面のテンプレと運用の約束は [x-operations.md](x-operations.md)。** PATCH だけのリリースは告知しなくてよい（更新履歴に残れば足りる）。

## 規約・ポリシーを改訂するとき

1. `src/pages/legal/TermsPage.tsx` / `PrivacyPage.tsx` を直す
2. `src/lib/site.ts` の `LEGAL_REVISED_DATE` を更新する（`LEGAL_EFFECTIVE_DATE` は最初の施行日のまま動かさない）
3. CHANGELOG に「変更」として載せる（MINOR 以上）
4. **情報の扱いが変わる改訂**（解析ツールの追加、外部送信の追加など）は、X でも告知する

プライバシーポリシーの「ブラウザに保存される情報」の表は `src/pages/settings/lib/storedItems.ts` の台帳から生成している。**保存キーを増やしたら台帳に足すだけでポリシーにも出る。** ポリシー側を手で書き足さないこと。

## 外部への通信を増やすとき

現在、ページを開いたときの外部通信は **Cloudflare Web Analytics のビーコン1本だけ**。フォント・アイコン・画像・データはすべて自前配信になっている。

ここに何かを足す（CDN・埋め込み・外部 API）ときは、**プライバシーポリシー第5項を同時に直す**。直さないとポリシーが嘘になる。

- ビーコンは `VITE_CF_BEACON_TOKEN` が渡されたビルドにだけ入る（`vite.config.ts`）。
- 本番のトークンは GitHub の repository **variables**（secrets ではない。HTML に載る公開値）の `CF_BEACON_TOKEN` に置く。
- 手元のビルドや fork にはトークンが無いので、他人のビルドが集計に混ざることはない。

## やらないと決めたこと

- **コミットからの自動生成**（release-please 等）は使わない。Conventional Commits で書いてはいるが、開発者向けの文面がそのまま利用者に出るのが困る。履歴は手で書く。
- **GitHub Releases を正本にしない。** サイトの外に正本があると、リリース作成を忘れたときにページが止まる。Releases は CHANGELOG の写し。
- **裁判管轄を規約に書かない**（居住地が実質公開されるため）。準拠法だけ定める。
