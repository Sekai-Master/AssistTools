## 不可侵の制約（最初に読む）

**公式が公開していない情報を絶対に出さない。**

マスタDB は解禁前のカード・イベントを含む。2026-08-01 時点の上流に、実際に解禁5日前の
カードが1枚（id1439）入っていた。素通しすると、このサイトが情報解禁前の内容を世に出す。

- **実行時に隠すのではなくビルド時に落とす**。配信 JSON は誰でも開けるので
  「持っているが UI で出さない」は遮断にならない
- **早く出るくらいなら遅れる方を選ぶ**。先読みの猶予を一切入れない（解禁1秒前でも出さない）
- **存在を示唆する経路も塞ぐ**。カード本体を消してもボーナス表に cardId が残れば
  「まだ見ぬカードがある」ことも「それがPU対象である」ことも漏れる
- **画像の取得も同じ扱い**。サムネイルは「派生データに残ったカード」だけを起点に落とす。
  未公開カードのアセットは**要求もしない**（取得のログ自体が痕跡になる）。
  実行時に外部CDNを叩かせるのも不可（配信の生死・権利・オフラインのどれでも困る）
- 最後に検算し、痕跡があれば**書き出さずに落ちる**

実装は `scripts/lib/deriveCardData.mjs`、テストは同 `.test.mjs`（19件）。

「未実装カードの仮置き」機能は**ユーザーが自分で定義する**形にする（DB から引っ張らない）。

## 確定した式

### イベントボーナス（実装済み・実編成2つで完全一致）

```
カードごと = キャラ属性ボーナス + レアリティ×マスターランク + カード個別(PU)
合計 = Σ カードごと + WLサポート(手入力)
```

**★ キャラ属性ボーナスは「一致する行を足さない」。** 「キャラ+属性」の行は合算済みの値
（実測: キャラ25 + 属性25 に対して 両方=50）。全部足すと 100 になり倍以上に膨らむ。
**最も具体的に一致する1行だけ**を採る（両方 > キャラ > 属性）。

- 属性の行を持たないイベントがある（実測 207・211）
- VS のキャラは複数ユニットに跨る。`supportUnit` でどの枠かが決まる
- リーダー専用の上乗せはそのカードがリーダーのときだけ
- 対象人数の上限を超えたぶんは効かない（残すのは大きい順）

検証: **315% / 260% とも実機と完全一致**。

### 総合力（実装済み）

```
総合力 = パフォーマンス
       + Σ パラメータ毎 floor(値 × エリア倍率)        ← エリアアイテム
       + Σ パラメータ毎 floor(値 × キャラランク率)     ← CR
       + Σ カード毎     floor(パフォーマンス × ゲート率) ← ゲート
       + Σ カード毎     floor(パフォーマンス × 家具率)   ← 家具（そのキャラのカードだけ）
       + 称号（プレイヤー固有の固定値・編成に1回）

パフォーマンス = 基礎値(レベル) + 特訓 + マスターランク + サイドストーリー + キャンバス
エリア倍率     = ユニット効果 + タイプ効果 + キャラクター効果
                 5枚全員が同じユニット枠 → ユニット効果を2倍
                 5枚全員が同じ属性       → タイプ効果を2倍
```

**★★ ％の計算は float32 でやる。★★**
ゲーム本体が float32 で計算しているので、`rate * 0.01 * base` と書くと実機と1ずれる。
float32 では 0.01 が 0.009999999776… になり、5% は 0.049999998882… になる。
ちょうど割り切れる値で floor が1つ下がる（11540 の5% は 577 ではなく 576）。
**必ず `ratePower()` を通すこと。** これが「CR 5% だと実測より1多い」の正体だった。

**★ 丸めの単位が項目ごとに違う（実測でそう出ている）。**
エリアとCRは**カードごと・パラメータごと**、ゲートと家具は**カードごと・3パラの合計**、
称号は**編成に1回**。同じ％計算なのに違うが、単位を間違えると数十〜数百ずれる。

**★ 全一致は5枚揃って初めて付く。** 1枚・2枚では付かない（実測で確認済み）。

**★ マスターランクの加算は累積。** MR3 なら MR1・2・3 の行を全部足す。

**★ ユニット枠は1つだけ見る。** カードが VS のキャラでも、`supportUnit` があれば
そのユニットの効果しか効かない。エリアもゲートも同じ。

検証: **単体と5枚編成の両方で、全成分が実機と完全一致。**

| | 合計 | パフォ | エリア | CR | ゲート | 称号 |
|---|---|---|---|---|---|---|
| レン(471)単体 | 50,267 | 34,596 | 13,664 | 1,728 | 69 | 210 |
| レオニ5枚・クール染め | 236,756 | 129,838 | 99,968 | 6,483 | 257 | 210 |
| 同・一歌→MEIKO（純ピアプロ） | 215,593 | 129,838 | 78,832 | 6,456 | 257 | 210 |
| 同＋咲希のぬいぐるみ/S | 215,612 | 129,838 | 78,832 | 6,456 | 257 | 210（家具 19） |

- 単体のエリア 13664 は レオニ15% + キュート8.5% + レン16% ＝ 39.5% でぴったり合い、
  VS の 11% を足すと 17469 になって合わない（＝**ユニット枠は1つ**、が確定した根拠）
  - ★ ただし「1つ」がどちらかは、**この1件だけでは決まっていなかった**。下記 2026-08-12 参照
- 5枚のエリア 99968 は全一致を使わないと 69456 にしかならない（＝**5枚で2倍**の確認）
- 5枚のゲート 257 は、**カードごとに floor** して 74+65+61+39+18。編成の合計に
  1回だけ掛けると 259 になって合わない。咲希が 19994×0.2%＝39.988 で
  40 の直前に落ちるのが効いている

**★ 3件目は対照実験として質が高い。** 一歌(id 1)と MEIKO(id 101)はどちらも
1★Lv20/MR5/前後編読了で**パフォーマンスが 9225 で完全に同じ**なので、
動く変数がユニット枠だけになる。これ1回で4つ確定した:

1. 純ピアプロのカードには **VIRTUAL SINGER の +11% が乗る**
   （supportUnit 付きのレンには乗らなかったのと対）
2. **全一致はユニットとタイプで独立に判定される。** ピアプロが1枚混ざって
   ユニットの全一致は消えたが、5枚とも cool なのでタイプの全一致は残った
3. 純ピアプロのカードのゲートは**全ゲートのうち一番高いもの**（レオニ Lv2 の 0.2%）。
   ゲートが 257 のまま動かないのが証拠（効かないなら 239 に落ちる）
4. **キャラクターランク47 の 4.7%** が効く（上限50に達していないレートの初実測）

### ユニット限定カードのエリア枠は「効果が高いほう」（2026-08-12 確定）

VS のキャラが他ユニットの衣装を着たカード（`supportUnit` 付き・247枚。**VS 以外のキャラには存在しない**）は、
マスタの `unitCharacters` を見ると **piapro と6ユニット全部に行がある**。どの枠のエリア効果が乗るのかを実機で確定させた。

| 実機の編成 | supportUnit の効果 | ピアプロの効果 | 実際に乗った |
|---|---|---|---|
| ミク(21)・リン(22) のモモジャン衣装 | モモジャン **9%** | **11%** | **11%（ピアプロ）** |
| 622・900・471 のレオニ衣装 | レオニ **15%** | 11% | **15%（supportUnit）** |

**＝ 効果が高いほうだけが乗る。足し算ではない。**

- 片側だけの観測なら「常に supportUnit」でも「常に piapro」でも説明できてしまう。
  **両側が揃って初めて決まる**ので、どちらの向きの実測も台帳に残してある
- 「常に piapro」にすると、レオニ衣装を含む編成が3万近くずれて壊れる
- **この誤りは長く潜んでいた。** ミク・リンのモモジャン衣装を編成に入れるまで一度も表に出ず、
  出たときは「エリアだけ 1,335 足りない」という形で現れた

**★ ゲートはこの規則に従わない。** 同じ編成でゲート 401 は supportUnit 側（モモジャン）の値で一致した。
**エリアとゲートで枠の決め方が違う**。`power.ts` では `areaUnitOf()` と `resolveUnit()` に分けてある。

**★ 全一致ぶんは効果一覧に出ていないが、マスタ上は必ず通常の2倍**（ユニット・タイプ）。
キャラのアイテムは全一致でも増えない。配信データの全行でそうなっていることを
`power.real.test.ts` が毎回確認しているので、`areaRatesFromEffects()` で 2 倍にしている。
おかげで**入力はゲーム画面の数字をそのまま写すだけで済む**。

- サイドストーリー: 前編+250 / 後編+600（1パラメータあたり）。4★読了で総合力+2,550/枚。
  **入れ忘れると1編成で1万以上ずれる**
- キャンバス: 1枚ごと（4★ +1,500）。レアリティで額が違う
- キャラランク: 47 なら 4.7%（実測）。**CR50 で上限5%**、それ以上は伸びない
- ゲート: `mysekaiGateLevels` に Lv1=0.1% 〜 Lv40=4%。率は5基とも同じ。
  **ゲートは5基のみでピアプロには無い**ので、純ピアプロのカードは
  **全ゲートのうち一番高いもの**を採る（実測）。
  ユニット枠を持つカードはそのユニットのゲートだけを見る

### 発揮可能総合力の上限（ワールドリンク第3弾）

**編成の総合力がある値を超えても、超えたぶんはスコアに乗らない。** 実測はどの回も 336,000。
スコアが頭打ちになるので、スコアから出るイベントPtも頭打ちになる（協力・ソロ・オートすべて）。

```
スコアに渡す総合力 = min(編成の総合力, upperTotalPower)
```

出典はマスタDB `eventTotalPowerLimits.json`（`eventId` × `upperTotalPower`）。
ゲーム側の言い方は「**発揮可能総合力**が33.6万に制限」。

#### ⚠️ 「ワールドリンクなら一律で掛かる」ではない

| | 件数 |
|---|---|
| `eventType === "world_bloom"` のイベント | **18** |
| そのうち上限があるもの（202/205/207/211/214＝WL第3弾） | **5** |
| 上限があって world_bloom でないもの | **0** |

旧ワールドリンク（「水底に影を探して」「泡沫に抱かれて」など13回）には上限が無い。
**`type === "world_bloom"` で代用すると、上限の無い過去イベントまで巻き込んで計算を誤らせる。**
判定は必ず `powerLimit` 欄の有無で行う（`src/lib/powerLimit.test.ts` が
「world_bloom の方が真に多い」ことをテストで固定している）。

#### 実装の勘どころ

- **クリップするのはスコア式に渡す直前だけ。** 総合力の表示（`PowerPanel` の「実機との差」）は
  実機と突き合わせて積み上げてきた検算資産なので、`deckPower()` の返り値を丸めてはいけない
- 差し替え候補も横並び比較も `compareDecks` を通るので、**上限は `CompareCondition` の1箇所**で効く
- 上限帯では**このツールの主張がそのまま逆になる**。「ボーナスを5%落として総合力を盛る」が
  売りだが、盛ったぶんが1点にもならないので、入れ忘れると**損をする編成を「最良」として勧める**
  （`compare.test.ts` の「上限があると…ボーナスを取った編成が勝つ」がこれを固定している）
- チャレンジライブとカスタム条件では効かせない（どちらも実在イベントの制約から外れる）

#### 配信ファイルを分けている理由

上限は効率曲ランキング（`/ranking`）でも要るが、そちらに `bonuses.json`（270KB）を読ませるのは
「各ツールが編成ビルダーのデータを直接読むとどのページも重くなる」という既存方針
（`src/lib/profiles.ts`）に反する。判定に要る最小限だけを
`public/CardDatas/powerLimits.json`（5行・625バイト）に切り出して配っている。

#### 兄弟の制限（214には効かない）

同じ系統の表が3つあるが、**すべて eventId 180「Wishes in Bloom！」だけの一発**で、
現行の WL第3弾には付いていない。実装していない。

| 表 | 内容 | 対象 |
|---|---|---|
| `eventCardBonusLimits` | ボーナス対象メンバー数 4人 | 180のみ |
| `eventSkillScoreUpLimits` | スキルのスコアアップ 240% | 180のみ |
| `eventMysekaiFixtureGameCharacterPerformanceBonusLimits` | マイセカイ設置物 20% | 180のみ |

※ `bonuses.json` の `bonusLimits` は `eventCardBonusLimits`（メンバー数）であって
総合力の上限ではない。**名前が近いので混同しないこと。**

## 実測で分かった細かいこと

### イベントボーナスは表示が切り捨て

レオニ5枚・クール染めの編成で、ゲーム内のカードごとの表示は
**50 / 30 / 25 / 26 / 25.5** なのに、合計の表示は **156%**（156.5% ではない）。
`eventBonus.ts` の計算値は 156.5% で、**カードごとの値は表示と完全に一致している**。

→ 内部は小数を持っていて、**合計の表示だけ切り捨てている**。
比較のときは小数のまま使い、画面に出すときにどうするかは別に決める
（ゲームと同じ 156% にするか、正確に 156.5% と出すか）。

### 家具ボーナスの上げ方と単位

普通の家具をいくら作っても上がらない。**ボーナスを持つのは「◯◯のぬいぐるみ」と
「◯◯のダイヤモンドオブジェ」だけ**（1499個中525個）。サイズで率が決まり、
**置いたキャラのカードにだけ**乗る（編成全体ではない）。

| サイズ | マスタの bonusRate | 実際の率 |
|---|---|---|
| S | 1 | **+0.1%** |
| M | 3 | +0.3% |
| L | 6 | +0.6% |

**★★ マスタの 1/3/6 は % ではなく 0.1% 単位。★★**
実測: 咲希のぬいぐるみ/S を1個置いたら、咲希のカード合計 19994 に対して **+19**。
1% なら 199 になる。ここを % として扱うと家具ボーナスが10倍に膨らむ。
（先駆者の実装が `×0.001` を使っていたのはこのため。当時は理由が分からなかった）

`mysekaiFixtures.mysekaiFixtureGameCharacterGroupPerformanceBonusId` →
`mysekaiFixtureGameCharacterGroupPerformanceBonuses` → `mysekaiFixtureGameCharacterGroups`
と辿るとキャラと率が引ける。1キャラあたりの理論上限は 60〜70（＝**6〜7%**）。
`PlayerState.fixtureRates` は **% で受ける**ので、S 1個なら `0.1`。

### 「351 vs 350」の正体

前の引き継ぎに残っていた「ゲートの丸めが編成1（5枚）だけ 351 vs 350」は**解決済み**。
別の5枚編成（レオニ・クール染め）で 257 が完全に一致した。原因は丸め方ではなく、
**カードごとのパフォーマンスの内訳を取り違えていたこと**だったと思われる
（特訓やマスターランクの入力が1枚ぶんずれると、合計は合っていてもカード単位の
floor が変わってゲートだけ1ずれる）。

## このツールの存在意義（見失わないこと）

**「ボーナスを5%落として総合力を盛った方が、最終的なイベントPtで勝つ」を出せること。**

ゲーム内の「おまかせ編成」はボーナスしか見ないので、そこは絶対に埋まらない穴。
逆に言うと、**ボーナス最大化だけでは差別化にならない**（おまかせで足りる）。

スコア→イベントPt の式は**ランキングとアナライザーに既にあってテスト済み**なので、
比較機能は主に配線で済む。

## 検証の作法（効いたやり方）

- **正解は Nori の実機の数字**。モデルレビューより実測が強い
- **変数を1つずつ動かす**。単体編成 → 2枚 → 5枚、ゲートのレベルを1上げる、という
  差分の取り方で全部の式が割れた。同じ形の編成をいくら集めても分からない
- **未入力を0と混同しない**。MR の記載が無い編成を0として計算し、5%ズレの原因を
  「データと実機の食い違い」だと疑って仮説を3つ立てたが、ただの入力漏れだった
- **合った例だけ集めない**。実測が合ったあとに Fable-B で「それでも間違っている編成が
  あるはずだ」と探させる予定（まだ未実施）
- **先に先駆者の実装を読むのがいちばん速かった**。float32 の件は実測の差分からは
  「4.999999% なら合う」までしか出ず、理由に辿り着けなかった。他人のコードに答えが
  書いてあった。自分で式を割る前に GitHub を探す
- **同じ強さのカードを差し替えると対照実験になる**。一歌と MEIKO はどちらも
  1★Lv20 でパフォーマンスが 9225 で完全に同じだったので、1枚入れ替えるだけで
  「ユニット枠だけが違う編成」が作れた。1回の実測で4つ確定した
- **仮説を並べて実測にぶつける**。「エリアはユニット枠を1つ見るのか両方見るのか」は、
  候補を3つ計算して 13664 / 12280 / 17469 と並べたら一発で決まった。
  1つの仮説を検証しようとするより、候補を全部出して実測と照合する方が速い
- **実測から編成を逆算できる**。カードの基礎値は配信データにあるので、
  「パフォーマンス 34596」から総当たりでカードと育成状態を特定できた（レン id 471）。
  実測のメモにカード名しか無くても、後から検算に使える

### スキル値（2026-08-02 追加・実機と一致を確認済み）

カードが1意に決まるので、**スキルレベルを入れれば内部値も実効値も計算できる**。
他のツールが手入力していた「150/710」を編成ビルダーは自前で出せる。

- マスタのスキルは**21種の原型**しかなく、全カードが `skillId` で共有している
- 値は「そのスキルレベルでのスコアアップの**上限**%」。条件付き（ライフ依存・
  GOOD を出すまで・PERFECT のみ）は上限側を採る。ゲーム内のスキル説明も
  「最大◯%」で書かれていて、そこと突き合わせられる
- **編成で変わるスキルがある**（同ユニット1人ごと+10%・全員一致でさらに+10% /
  自身と異なるユニット1種類ごとに+30%・最大2種類 / 他メンバーのスキル値の50%・上限60）。
  5枚が分かる編成ビルダーだけが正確に出せる部分
- ★ 派生データに残すスキルは**公開済みカードが実際に使っているものだけ**。
  この表は日付欄を持たないので、素通しすると未公開カード専用の新スキルの
  説明文がカード本体より先に出る（`auditLeaks` で見張っている）
- 実効値（協力）は `multiEffectiveSkill`（効率曲ランキングと同じ式）を呼ぶだけ

### 編成の種類（2026-08-02）

- **イベント編成**: 同じキャラを2枚入れられない（同じカードはもちろん、ミクのレオニ枠と
  VS枠のような別カードでも不可）。組めない編成の数字を出しても意味が無いので選べなくしてある
- **チャレンジライブ**: 条件が**正反対**で、同じキャラのカードだけで5枚組む。
  イベントポイントが無いので、ボーナスの計算ごと外して比較もスコアで行う
- 切り替えると枠を空ける（残すと、その種類では組めない編成のまま数字が出る）

### イベントボーナスの「カスタム」（2026-08-02）

対象メンバーとタイプを自分で置ける。「次がこのメンバー・このタイプだったら手持ちで
組めるか」を試すためのもの。**計算式には手を入れず**、条件から `deckBonuses` 行を
組み立てて実在イベントと同じ経路に流している（`lib/customEvent.ts`）。

- 配分の既定は 25 / 25 / 50（近年の標準）。変えられる
- カード個別（PU）と対象人数の上限は持たない。誰がPUかは決めようがないため
- ここで入れるのは利用者が考えた条件で、配信データは見ない（不可侵の制約とは無関係）

### 紹介カード（PNG・2026-08-02）

`lib/deckCanvas.ts`（描画）と `lib/share.ts`（何を載せるか・テストあり）に分けてある。

- 地の色と右端の半円の光は**リーダーの属性色**。クール染めなら青くなる。全体は 16:9
- **立ち絵とイベントロゴはビルド時に落として自前配信**（`public/CardDatas/{art,logo}`）。
  ★★ 実行時に配信元から取ることはできない。**あちらは Referer 付きの要求を 403 で
  弾く**（他サイトからの直リンクを意図的に塞いでいる）。ブラウザは画像取得で必ず
  Referer を送るので通らない。`referrerPolicy` で回避はできるが**しない**（Nori 判断）
- 立ち絵は容量の都合で**★4と birthday だけ**（1584枚・23.6MB）。★3以下がリーダーの
  ときはサムネイルだけの簡易版に落ち、その旨を画面に出す
- マスターランクはゲームと同じくカードの左下にひし形（上が緑・下が暗い灰・銀の縁）
- ★ ユニット色は `light-dark()` で定義されていて canvas が解釈できない。
  解決済みの色に直してから渡すこと（渡さないと `addColorStop` が例外を投げ、
  **描きかけの真っ黒な画像**が出る。実際にやった）

### UI で決めたこと（実装済み・変えるなら理由を残すこと）

- **育成状態はカードに紐づけて保存**する（`sekaimaster:deck:cards:v1`）。編成に持たせると
  「編成Aで直したのに編成Bが古い」が必ず起き、しかも画面はそれらしく見えて気付けない
- **プレイヤー設定は「ゲーム画面から写した生の値」で保存**する（`AreaEffects` の形のまま・
  家具は率でなく個数）。計算に都合のいい形で保存すると、式が変わったとき保存済みデータが
  意味を失う。変換は `playerStore.ts` の `toPlayerState()` で毎回行う
- **マスターランクだけ既定値を置かない**。未設定のまま持って画面に「未設定」と出す
- 比較の**スキル値は全編成共通**。配信データにスキルの表が無く、カードから出せないため。
  画面に明記してある。総合力とボーナスの比較には効かない
- 画面の合計ボーナスはゲームと同じ**切り捨て**、比較と保存は**小数のまま**
- 実測との突き合わせは `playerStore.test.ts` が担当する。**画面と同じ経路**（保存形式 →
  変換 → 計算）で 236,756 / 215,593 / 215,612 に一致することを固定している
  （`power.real.test.ts` は計算モジュール単体、こちらはその手前の詰め替えまで込み）
